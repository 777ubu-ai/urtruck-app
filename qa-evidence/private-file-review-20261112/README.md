## Модель доступа в кандидате

- Для вложения сделки сервер требует авторизованного пользователя, существующую комнату, участие пользователя, разрешённое состояние сделки и точную связь `attachment_id → conversation_id`. Проверяются запись загрузки, отправитель/участник, сообщение и допустимая цель хранения. Сервер читает байты сам, повторно проверяет связь после чтения и отвечает `private, no-store`/`nosniff`.
- Для фото и голосового сервер требует участника конкретной комнаты, принятую сделку и связь `message_id → room_id`; после чтения связь проверяется повторно. Ответ не кэшируется.
- Клиентские защищённые пути находятся в `src/utils/privateFileTransport.js`; экранов чата/PDF вызывают их через `src/screens/DealWorkspaceScreenV2.js` и `src/components/deal/DealAttachments.js`.
- Основная реализация: `backend/api/deal_room.py` (`GET /api/v1/chat/conversations/{conversation_id}/attachments/{attachment_id}/content`) и `backend/api/chat.py` (`GET /api/v1/chat/messages/{room_id}/media/{message_id}`).

В `backend/services/file_signing.py` локальная ссылка подписывается HMAC по ключу файла и `exp`; проверка действительности ссылки сама по себе не знает ACL комнаты. Для Supabase создаётся bearer URL с заданным сроком, обычно 86400 секунд; кэш повторно использует URL ограниченное время, но не продлевает уже выданный URL. Локальный срок ограничивается `storage_service.create_signed_url` диапазоном 60 секунд—7 суток.

**Важно:** фактический TTL runtime нельзя подтвердить исходным кодом кандидата. Хэш `backend/api/deal_room.py` на обоих серверах отличается от локального кандидата, а защищённые content/media пути не развернуты. Уже выданные production/QA2 ссылки не извлекались и не тестировались; поэтому неизвестно, какие конкретно ещё действуют. По текущему коду ссылки, выданные старыми ответами, могут сохранять доступ до своего `exp` даже после смены статуса комнаты. Supabase-ссылку нельзя индивидуально отозвать без изменения политики/ключей или удаления объекта; эти действия здесь не выполнялись.

## Исторические клиенты и совместимость

Известные ранее загруженные Android source `ac015acce807dc2ca931beb7df61b203c554156d` и iOS source `a2258821…` не содержат `privateFileTransport`; старый `PdfPreviewContent` открывает URL напрямую. Точный source последних публичных Android/TestFlight артефактов не привязан к их бинарным метаданным в доступном отчёте. Тестировочные/публичные клиенты, которые продолжают читать `url`/`photo_url`, зависят от legacy signed URL. Поэтому старые поля и выдача не отключались.

Тестируемый переход без поломки истории:

1. Развернуть backend защищённых endpoint’ов только в QA2 через штатную интеграцию и backup.
2. Проверить новые client пути на обеих ролях и госте/постороннем, используя выделенные QA2 аккаунты и реальные QA2 объекты; сравнить содержимое/хеши.
3. Оставить legacy выдачу на явно измеренный период совместимости, логируя только агрегаты факта выдачи и версию клиента (без URL/ключей).
4. После установления максимального TTL всех действующих signer’ов прекратить выпуск новых legacy-ссылок в QA2, дождаться `max TTL` с момента последней выдачи, затем проверить отказ старой ссылки при сохранении доступности через новый endpoint.
5. Только после независимого review и согласованного релизного шага спланировать аналогичный переход в production. Не менять общий ключ и не удалять объекты.

Пункт 4 пока непроверяем: runtime TTL старого production/QA2 signer’а не установлен, действительные URL не проверялись, а в приложении нет индивидуального механизма отзыва уже выданных bearer URLs.

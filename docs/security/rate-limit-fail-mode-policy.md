# Fail-mode policy для rate limiter'ов (C1.5)

Дата: 2026-09-08 · Security-спринт C1.1/C1.5 · baseline `c4501ece`

Аудит выявил противоречие: лимитер в `backend/api/middleware.py` при
недоступном Redis делал `return` (fail-open), то есть сбой инфраструктуры
молча снимал защиту. Лимитер при этом никуда не был подключён (мёртвый код).
Этот документ — единый источник истины, как ведут себя лимитеры при сбоях.
Краткая версия продублирована docstring'ом в `backend/api/middleware.py`.

## Правила

### 1. OTP / auth / admin — FAIL-CLOSED

Класс: security-критичные входы (OTP send/verify, admin Basic Auth, вход по
паролю/email-коду).

- Хранилище счётчиков недоступно (SQLite sidecar повреждён/недоступен,
  будущий Redis недоступен) → запрос **отклоняется 503** + запись в лог с
  указанием операции и scope.
- Проверка доступности хранилища выполняется **до** бизнес-логики; исключение
  `RateLimitUnavailable` не глотается.
- Рациональное обоснование: для входов ущерб от временной недоступности
  (легитимный пользователь подождёт 15 минут / повторит позже) меньше ущерда
  от снятия лимита во время инцидента (онлайн-брутфорс админки, SMS-фрод).

### 2. Прочие write-endpoint'ы — FAIL-OPEN с логом

Класс: отзывы, жалобы, избранное, guest-сессии, создание листингов/ставок
(когда лимитеры там появятся).

- Отказ лимитера не должен ронять пользовательский сценарий: запрос
  выполняется, ошибка пишется в лог, сигнализация — через мониторинг логов.
- Текущий in-memory лимитер (`backend/api/rate_limit.py`) этому следует:
  чистый dict физически не «падает»; его failure mode — потеря счётчиков
  при рестарте процесса (см. «Ограничения»).

### 3. Read-only и служебные пути — без auth-класса лимитов

`/health`, `/api/version`, `/storage/{path}` по валидной подписи,
Telegram webhook, мониторинговые endpoint'ы лимитерами auth-класса **не
затрагиваются**. Иначе внешняя брутфорс-атака на /admin заблокировала бы
внутреннюю автоматизацию (healthchecks, scheduler, uptime-мониторинг).

Админский лимитер живёт строго внутри `check_admin` (backend/api/admin.py)
и применяется только к роутам `/admin`.

## Реализации

| Лимитер | Файл | Хранилище | Fail-mode |
|---|---|---|---|
| Admin Basic Auth: 5 неудачных/IP → блок 15 мин, 429 + Retry-After | `backend/api/admin.py` + `backend/api/persistent_rate_limit.py` | SQLite sidecar `<DB stem>.ratelimits.db` (переживает рестарт процесса) | fail-closed 503 |
| OTP send/verify, guest, reviews, reports | `backend/api/rate_limit.py` | in-memory dict | de-facto fail-open (не может упасть; теряет счётчики при рестарте) |

## Что сознательно не сделано (и почему)

- **Redis-лимитер не подключён.** Код в `middleware.py` был мёртвым
  (нигде не импортировался) и fail-open — удалён с комментарием. Redis в
  деплое нет; поднимать инфраструктурную зависимость ради счётчиков
  неудачных логинов — лишняя точка отказа. Путь масштабирования: общий
  per-IP лимит через `app.add_middleware` при появлении Redis, с fail-closed
  для admin/OTP и fail-open для прочих.
- **OTP/verify counters не перенесены в SQLite.** Существующий in-memory
  лимитер имеет компенсирующий DB-guard (5 attempts на код на уровне БД,
  `verification_codes.attempts`, переживает рестарт), поэтому приоритет был
  отдан админке. Миграция OTP-счётчиков на sidecar — follow-up.
- **Лимиты на chat/bids/listings не добавлены** — отдельный скоуп спринта;
  при добавлении применять правило 2 (fail-open с логом).

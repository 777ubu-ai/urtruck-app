## Подтверждённая причина сбоя истории

Комната `240865c8-a0ed-490d-b540-774e9b973688` корректно связана со сделкой
`1c26ef04-3b99-4071-aa6f-c650ca11af76`: Serik — driver, Boris — shipper.
На сервере 24 сообщения, включая 4 голосовых. Позже история появилась
на Xiaomi без изменения связей комнаты и сделки: это не доказательство
постоянной ошибки room_id.

В error-log production зафиксирована цепочка:
`get_messages → file_signing.sign → storage_service.create_signed_url → httpx.ReadTimeout`.
Исключение при подписи одного вложения прерывало выдачу всей истории.
Клиент скрывал ошибку загрузки; первоначальный пустой массив отображался
как «Сообщений пока нет». Отдельно этот текст показывался во время первой загрузки.

## Минимальное исправление

1. Backend сохраняет выдачу текстовой истории при сбое подписания вложения.
   Приватный исходный ref не выдаётся: URL становится null, появляется
   `attachment_unavailable`. Следующий poll повторяет подписание.
2. После первого сбоя в пределах ответа не выполняются повторные медленные
   запросы подписания остальных вложений. Это ограничивает накопление timeout,
   но не устраняет сетевую причину недоступности storage.
3. Frontend различает загрузку, успешную пустую комнату и ошибку с кнопкой повтора.
   Уже загруженная история сохраняется при временной ошибке.
4. Параллельные polling-запросы одной комнаты/сессии не накапливаются.
   Поздние ответы и ошибки другой сессии игнорируются.
5. Недоступное вложение имеет явную подпись; новые строки доступны RU/EN/KK/ZH.
6. Проверки участия, принятой сделки, приватности и исходные файлы в БД не менялись.

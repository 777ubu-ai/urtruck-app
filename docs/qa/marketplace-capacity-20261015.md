## Воспроизведено и исправлено

1. /my отдавал лишь последние 50 грузов/рейсов без пути к следующим. Если последние объявления архивные, экран показывал 0 активных при наличии 4900 активных в БД. Добавлен owner-only GET /my/listings: фильтр раздела до LIMIT, точный archive_total, фиксированные страницы и детерминированная сортировка created_at/id.
2. Public feeds повышали limit вместо offset. Реальный API на запрос limit250 возвращал 200; следующие объявления были недоступны. Клиенты теперь передают limit50 и offset; backend возвращает next_offset, сортировка published_at/id стабильна при одинаковом времени.
3. Hygiene/expiry и исключение своих объявлений могли сделать видимую страницу неполной/пустой. Конец выборки теперь определяется по серверному окну до hygiene, а не по числу видимых карточек.
4. Добавлены блокировка двойной подгрузки, дедупликация по ID, защита от позднего append/refresh, повтор ошибки без потери списка. Feed фильтры стран включены в зависимости запроса. Для новых страниц используется локализованная кнопка «Показать ещё» (own-list hit target не меньше44dp); автоматического каскада запросов при пустых фильтруемых страницах нет.

Старый /my и shared cache/unread не изменены. Для старого backend только 404 нового owner endpoint допускает прежний dashboard fallback с paginationUnavailable=true; это совместимость, а не доказательство масштаба. 5xx/сеть не маскируются пустым успехом. Новые owner ответы от прежнего bearer отбрасываются.

## Изолированный capacity probe

Воспроизводимая команда (Python с backend test dependencies):

```sh
python scripts/qa_capacity_probe.py . /tmp/urtruck-capacity-result.json
```

Процесс очищает environment до импорта приложения, создаёт уникальную временную SQLite, запрещает соединения с любой другой БД и исходящие IPv4/IPv6 соединения. Используются настоящий marketplace router и TestClient; production .env/main.py/scheduler не запускаются. Fixtures пишутся только в синтетическую БД. Исходные business data не читаются и не удаляются.

Сценарий A: один отправитель с 5000 грузов, один водитель с 5000 рейсов. Все 5000 уникальных записей каждого вида доступны через 100 страниц. Archive/owner isolation PASS.
Сценарий B: 5000 отправителей + 5000 водителей с отдельными регистрационными профилями, по одному объявлению; reviews schema включена, профиль водителя действительно читается и verified проверяется. Public API возвращает все 5000 уникальных записей каждого вида через 100 страниц.

## Ограничения и оставшиеся задачи

Offset pagination гарантирует полноту для неизменяемого набора; при изменении статусов/удалении записей другой сессией нужен refresh с первой страницы. Snapshot isolation всего многозапросного просмотра не заявляется. Ни один ответ не отдаёт сразу весь массив из5000.

Fixtures не содержат фотографии/вложения; размер медиа-кеша не измерялся. Сценарий относится к объявлениям, а не к5000 сделок/чатов. Не проверены реальные 10000 пользователей онлайн, конкурентные записи/accept/chat/push/GPS, мобильная сеть, native scroll FPS/RSS и длительное удержание приложения. Для этого нужен отдельный staging/physical performance pass; production не наполнять синтетикой.

Не закрыты отсутствием воспроизведения исходные P1 «Доставлен»/native freeze карты. Сохранены ограничения PR536: вес10000т, повторы PDF по attachment IDs, GPS/ETA и карточки требуют соответствующих данных/проверок. Нельзя написать «всё исправлено» или RELEASE_READY по этим нагрузочным проверкам.

Production/push-sync/магазины, IPA99/AAB214116271, Apple submission, реальные сделки/вложения не затрагивались. Мобильные сборки не создавались. Финальный verdict этого scope: SOURCE + LOCAL CAPACITY/WEB PASS; REVIEW/CI и PHYSICAL QA — отдельные gates.

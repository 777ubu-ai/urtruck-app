# FEED-13: проверка review-выборки

Срез: 2026-11-02, 13:33–13:36 UTC. Сервер QA2, установленный SHA `4d3525ff8d29d0204ed76aff49306c326972defb`.

## Метод и результат

Взята случайная выборка 200 доставленных сегментов со статусом API `review`, распределённая по 13 хешированным источникам. В исходнике не сохранялись и не выводились телефоны, полные тексты, идентификаторы авторов и имена источников. Все 200 сегментов повторно прогнаны текущими parser/classifier/API core-field правилами без записи в базу и без изменения очереди.

- 200/200 остались `review` при повторном прогоне текущим кодом.
- По проверенным полям в этой выборке: 67 без извлечённого маршрута груза, 64 без распознанного телефона, 45 без обоих обязательных полей. Категории пересекаются.
- У 62/200 текущий classifier всё ещё возвращал неразрешённое намерение; большинство таких причин — `unrecognized_intent`.
- Среди оставшихся сообщений встречались `ambiguous_route`, `ambiguous_route_sections` и `invalid_route_value`; текущий код не отправил их в обе ленты и не объявил активными.
- Автоматический повторный разбор не выявил кандидатов, которые одновременно проходят текущую проверку типа, маршрута/местоположения и телефона.

## Ограничения

Это автоматическая повторная проверка 200 реальных сегментов, а не ручная разметка 200 сообщений. Источники покрыты 13 хешированными группами из выборки; полнота охвата каждого настроенного Telegram-источника отдельно ещё не подтверждена. У 92 278 текущих QA2 review-карточек в последнем агрегате не было сохранённой причины review; установить их причины без повторного разбора исходников нельзя. Массовый replay или перевод review в active не выполнялся.

Следующий безопасный шаг для полной ручной проверки — повторно разобрать актуальные неистёкшие источники на QA2-кандидате в ограниченной диагностической партии, сохранить только обезличенные примеры и точные причины, затем адресно переиграть только подтверждённые подходящие записи с сохранением исходных дат и идентичности.

# Исправление напоминаний и подготовка управляемого scheduler

База: `qa2/integration-candidate`, `e062269de66e06a50cb1ba02be9d015aa513b3cb`.
Исходные доказательства: `qa-evidence/URTRUCK-PUSH-AUDIT-20261105/REPORT.md` и независимая проверка от 05.11.2026. Исторические результаты не переносятся на новый кандидат.

## Поведение

- no_bids — один логический повод на тип+ID объявления, общий для inbox/outbox; обычное редактирование и повторная публикация того же ID не сбрасывают историю.
- BEGIN IMMEDIATE сериализует проверку владельца/активности/срока/реальных ставок и создание inbox/outbox/claim. Ошибка постановки откатывает всю операцию.
- Старый inbox или попытка в push_log учитываются независимо от даты, без replay. История не удаляется. Старые необязательные outbox без корректного ID подавляются при доставке, а не переотправляются с новым ID.
- no_bids, inactivity и lifecycle — независимые preferences, выключенные по умолчанию. Сообщения, ставки, сделки, документы и tracking не зависят от этих выключателей. Сохранённый маршрут имеет собственный notify; все его producer и отложенная доставка проверяют актуальное значение.
- Порог от published_at/fallback created_at; UTC datetime; единый 30-дневный срок, без привязки к дате выезда. Lifecycle сообщает об истечении только при фактическом expired. Архивные объявления старше суток не превращаются в новую рассылку при обновлении.
- Inline sender и worker используют один outbox claim. Retry ограничен и имеет backoff; успешные native и web цели не отправляются заново при частичном успехе другой цели.
- После timeout принятие провайдером может быть неизвестно. Сохраняется тот же event ID, но exactly-once показ ОС не обещается; killed iOS не защищён JS-cache. Неоднозначный повтор — отдельная попытка того же события, не новый бизнес-повод.
- Typed deal.status события получают приоритет и TTL каталога, а не generic deal_status.

## Миграция и совместимость

Additive таблицы в push_schema.sql: notification_preferences, notification_event_claims, push_web_delivery_log. Их создаёт штатный schema bootstrap. Регистрационные, ownership и logout handlers API сохранены; прежний checksum этой части дополнительно проверяется frontend-регрессией. Старые клиенты продолжают работать; для новых UI preferences нужен backend-first rollout. Мобильный binary не пересобирается ради серверных проверок.

Откат: revert commit к базе. Новые таблицы и историю оставить; старый код их игнорирует. Откат на старый scheduler снова открывает подтверждённый риск спама, поэтому автоматический production rollback без оценки причины не предлагается.

## APNs: подтверждённая подготовка запроса

Read-only probe 05.11 показал: в venv API и standalone scheduler JWT установлен. API production/QA2 имеет topic/auth и локально подписывает JWT P-256. У обоих standalone production scheduler отсутствуют topic и auth-поля. provider_not_configured формируется локально до HTTP; это не ответ Apple. Связать каждую историческую ошибку с PID невозможно по имеющемуся delivery_log.

Подготовлен `scheduler.runner`: сначала читает конфигурацию тем же способом и с тем же приоритетом внешнего environment, что API; затем проверяет явные environment/DB/lock, уже выполненную миграцию и локальную подготовку APNs. `--check` не записывает в БД, не импортирует API, не обращается в сеть. При ошибке readiness не маскируется успехом.

Шаблон `ops/systemd/urtruck-scheduler@.service` **не установлен и не запущен**. Он использует venv и конфигурацию выбранного экземпляра (`urtruck` / `urtruck-qa2`), без преобразования PEM escapes systemd. Выбор production-процессов и конфигурации требует отдельного разрешения владельца.

План согласованного инфраструктурного продвижения:
1. Снять before hashes, конфигурацию без значений секретов, список фактических job и владельца lock; объяснить существующие overlays, не менять RELEASE_SHA вместо проверки.
2. Проверить backup SQLite с отдельным restore/quick_check и сохранить текущие unit/PM2 definitions для rollback.
3. Развернуть через штатный PR/workflow на QA2, проверить schema и `runner --check`; выбрать одного владельца scheduler. У API выключить embedded jobs, у управляемого runner они включаются только в его процессе.
4. До запуска нового процесса снять старые scheduler с автозапуска и остановить только подтверждённые экземпляры в согласованном окне. Два PID сами по себе не доказывают дубли job. Не запускать параллельный scheduler с другим lock.
5. После разрешения production — те же backup/hash/readiness/health шаги. Этот PR сам не запускает deploy или остановку production.
6. На согласованных тестовых аккаунтах различать enqueue, provider accepted, device received и opened. Для нескольких scheduler-интервалов ускорять только изолированный стенд.

## Проверки и аудит продукта

`test_scheduled_notifications_integrated.py` использует полные producer/sender/gateway с настоящей SQLite; заменяется только внешний транспорт. Проверяет историю, несколько ролей/публикаций/устройств, гонки, late bid/close, UTC, preferences, lifecycle, partial/timeout/worker restart и web retry.

Проверка полного сохранённого production sender+gateway также выполнена на изолированной БД: два legacy вызова дали две попытки; новый producer/worker создал одну. AST-стенд из первоначального аудита не используется как замена этой проверке.

Точные финальные SHA, CI, устройства, результаты полного аудита и ограничения фиксируются во внешнем отчёте/checkpoint после завершения проверок. Общая готовность UrTruck, физическая доставка и production-исправление этим документом не объявляются PASS.

### Уточнение полного E2E

Старые сценарии сделки/email ожидали немедленно видимый Main, хотя согласованный первый вход открывает внешнюю ленту поверх него. Подготовка сценариев теперь закрывает её настоящей кнопкой Back; проверки сделки, ролей и подтверждения не удалены. Отдельные обязательные сценарии обеих ролей явно проверяют показ и закрытие первого входа. Сбой повторных локальных email-прогонов из-за накопленного rate limit не обходится: стенд использует новую изолированную БД, защита API остаётся прежней.

Read-only runtime показал `URTRUCK_ENV=qa` на существующем QA2. Entry point принимает этот прежний alias вместе с qa2, что отдельно проверено тестом. Это не изменение конфигурации сервера.

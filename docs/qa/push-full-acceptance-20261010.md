# UrTruck — полное ТЗ и приёмка push до 10/10
Дата: 10 октября 2026, время Алматы.
Исполнитель: разработчик / QA. Владелец принимает подтверждённый результат на телефонах.

## 1. Цель и границы результата
Проверить всю цепочку: событие → сохранение → очередь → провайдер → телефон → переход → отображение → прочтение → серверный unread → внутренний badge → значок приложения → очистка системного уведомления.
Обязательные устройства: OPPO, Huawei, iPhone владельца (водитель; build 96 по сообщению владельца).
QA2 OneSignal и production FCM/APNs проверять отдельными прогонами. Не смешивать их базы, аккаунты, package/bundle ID и доказательства.
10/10 здесь означает завершённую матрицу push. Это не оценка готовности всего продукта.
Нельзя обещать безусловную доставку при отключённых разрешениях, отсутствии связи или системных ограничениях.

## 3. Продуктовый контракт
Системное уведомление, числовой badge, внутренний unread и бизнес-событие — разные сущности.
Закрыть баннер / смахнуть уведомление не означает прочитать сообщение.
Открыть приложение не означает прочитать все чаты.
Открыть список сделок не означает прочитать сообщения внутри комнат.
Уведомления о предложениях считаются просмотренными после успешного отображения соответствующего списка / карточки по согласованной логике.
Сообщения считаются прочитанными после загрузки и фактического показа в активном чате; вход на экран с ошибкой сети не даёт права списать unseen.
Снять прочитанное уведомление означает убрать его из системного центра и непрочитанного состояния; текст чата и журнал события сохраняются.
Посторонние комнаты и непросмотренные предложения сохраняются.
При отсутствии unread системный значок исчезает; отрицательные значения запрещены.
Число сообщений нельзя считать по количеству баннеров: несколько сообщений могут объединяться в одно системное уведомление.
У каждого события должен быть достижимый источник внутри приложения. Недопустимо «13» на иконке при отсутствии объяснимых непрочитанных элементов.

## 4. Источник истины и формула счётчика
Сервер определяет unread для текущего пользователя.
Итог = непрочитанные входящие сообщения доступных комнат + непросмотренные учитываемые бизнес-уведомления.
Chat-уведомление, дублирующее то же сообщение, второй раз в итог не входит.
Свои сообщения, служебные записи без unread-семантики и события чужого аккаунта не увеличивают число.
Правила доступности архивных/отменённых сделок должны быть явными: доступное непрочитанное отражается в достижимом списке; недоступное не создаёт фантомное число.
Иконка и вкладка используют одну семантику; сокращение «9+» допустимо только как формат отображения.
Push передаёт абсолютное актуальное значение / версию состояния, а не безусловный локальный +1.
Ответ старого запроса или старый push не может воскресить уже прочитанное состояние.
Локальные оптимистические изменения сверяются с сервером после ACK, возврата в приложение, восстановления сети и смены аккаунта.
Для нескольких устройств одного аккаунта проверить согласование read-state и честно описать задержку фонового устройства.

## 5. Регистрация устройств и безопасность
Проверить уникальную установку, provider, token, package/bundle ID, environment, locale, enabled и last_seen.
Один аккаунт может иметь несколько устройств; одно событие доставляется один раз на каждое целевое устройство.
Повторная регистрация не создаёт дубли и не вызывает шторм запросов.
Rotation token заменяет старый; постоянная ошибка инвалидирует токен без бесконечных повторов.
Logout отключает прежнюю привязку; запоздавший register старой сессии не восстанавливает её.
Новый аккаунт не получает уведомления предыдущего.
Нельзя принимать произвольный user_id / external_id от клиента без серверной проверки.
QA2 и production строго раздельны.
В отчётах не хранить приватные ключи, bearer, полные push-токены, пароли и OTP.
Усиленная проверка: sender, receiver, посторонний аккаунт.
Посторонний не получает payload, чат, документы, GPS и детали сделки.

## 6. Подготовка стенда
Два разрешённых тестовых чата A и B и одно отдельное тестовое предложение.
Подтвердить участника и роль на каждом устройстве через действующий вход, без создания поддельных сессий.
Снять baseline: серверный unread, значок, внутренняя вкладка, центр уведомлений.
Проверить системные разрешения: notifications, banner, sound, badge, lock screen; Focus/DND, mute, scheduled summary.
Huawei: определить GMS/HMS и фактический канал доставки. Не объявлять HMS PASS по FCM-тесту.
OPPO/Huawei: зафиксировать launcher и поддержку числа / точки. OEM-ограничение отражать отдельно от внутреннего unread.
Записать Wi-Fi / мобильную сеть и время устройств.
Каждое сообщение имеет уникальную метку QA-PUSH-дата-сценарий-номер.
Диагностический push без сообщения проверяет только доставку; не используется как доказательство unread или чата.

## 7. Матрица состояния приложения
Каждый основной сценарий выполнить на OPPO и Huawei в обе стороны; на iPhone — как получателе и отправителе.
1. Активен тот же чат.
2. Активен другой чат.
3. Открыт другой экран UrTruck.
4. Приложение свёрнуто кнопкой Home.
5. Телефон заблокирован.
6. Приложение убрано из последних.
7. Холодный запуск после перезапуска телефона и первого открытия приложения.
8. Нет сети → сеть восстановилась.
9. Notifications отключены → затем штатно включены.
10. Focus/DND включён → выключен.
Force-stop Android проверяется отдельно от swipe из последних: нельзя требовать обхода системного запрета. После штатного запуска проверить восстановление.
Для каждой строки отдельно зафиксировать доставку, видимость, звук, badge, внутренний unread, переход, read ACK и очистку.

## 8. Баннер, звук и активный чат
В фоне / на другом экране: уведомление с правильным отправителем, событием и локализованным текстом; звук по разрешениям.
В активном чате: входящее появляется один раз без лишнего баннера этого же сообщения; read-state обновляется после отображения.
В другом активном чате: уведомление новой комнаты не подавляется как «уже прочитанное».
Системные уведомления о важных изменениях сделки не теряются из-за chat-suppression.
Не обещать звук в silent/DND и баннер при запрете OS.
Не путать отсутствие верхнего баннера с отсутствием доставки.
Не отправлять несколько одинаковых уведомлений через Expo, FCM и OneSignal одновременно.
Не использовать тест с одними data-only сообщениями как замену пользовательскому alert-сценарию.

## 9. Переход из push
Тап открывает нужную комнату / предложение / сделку.
Проверить foreground, background и cold start.
Дождаться восстановления сессии и навигации; pending tap ограничен по времени и очищается после обработки.
Повторный тап не создаёт дубли экранов.
Не открывать последнюю комнату вместо room_id из события.
Если аккаунт сменился, доступ отозван или объект удалён — безопасное понятное состояние; чужие данные не отображаются.
Push из production не ведёт в QA2, и наоборот.
Deep link не признаётся прочтением, пока целевой объект не загрузился и не отобразился.

## 10. Числовой контрольный сценарий
Baseline должен быть измерен; не предполагать начальный ноль у рабочего аккаунта.
При baseline 0: три сообщения в A, два в B, одно предложение = итог 6.
Открыть и прочитать A: итог 3; уведомления A исчезают, B и предложение остаются.
Открыть предложение и успешно показать его: итог 2; сообщения B остаются непрочитанными.
Прочитать B: итог 0, значок исчезает, внутренний unread 0.
При baseline N проверять соответствующие приращения и сохранность нетестовых элементов.
Повторно открыть A/B: число не изменяется.
Смахнуть уведомление B до чтения: серверный unread B сохраняется.
Открыть приложение на другом экране: непрочитанные сообщения сохраняются.
Сверить иконку, вкладку, карточку комнаты и серверную формулу на каждом шаге.

## 11. Автоматическая очистка и гонки
ACK указывает комнату и границу последнего реально прочитанного сообщения.
Удалять только системные уведомления этой комнаты, относящиеся к прочитанной границе.
В A читаются сообщения 1–3; сообщение 4 приходит во время ACK: четвёртое сохраняется, если ещё не показано.
Поздний badge=6 после подтверждённого badge=3 не возвращает старое число.
ACK повторён / таймаут / ответ потерян: идемпотентность и повторная сверка.
Нет сети при открытии: не очищать серверный unread без подтверждения; восстановить после сети.
Уведомления другой комнаты, предложения и рейса сохраняются.
Смена аккаунта во время ACK не очищает уведомления нового аккаунта.
Возврат в фон во время чтения не списывает невидимые новые сообщения.
Проверить групповые Android-уведомления: summary не остаётся один без детей и не удаляет чужие группы.
Проверить iOS: удаление точечных delivered notifications и badge-сверка; общий clear-all запрещён.

## 12. Бизнес-события
Проверить реальные штатные действия через UI / авторизованные API, не SQL-подделку статусов:
- новая ставка / встречное предложение;
- принятие / отклонение;
- новое текстовое сообщение;
- фото, документ, голосовое;
- начало рейса и изменение статуса;
- граница, доставка, подтверждение получения;
- отмена сделки;
- проблема GPS активного рейса, если событие предусмотрено.
Для каждого: правильный адресат, событие один раз, локализация, доступный объект, актуальный статус.
Свои действия не дают себе ложного unread.
Повторный запрос и конкурентное действие не порождают вторую сделку / второе событие.
Событие, которое нельзя безопасно вызвать на рабочей сделке, проверить на QA2 и отметить production pending.

## 13. Очередь, устойчивость и диагностика
Событие атомарно сохраняется с outbox; падение процесса не теряет доставку.
Worker жив, очередь не накапливается без причины; pending/retry/dead имеют явный статус.
Повторы с backoff, TTL и разделением временных / постоянных ошибок.
Crash после provider-acceptance: контролируемая дедупликация; внешняя доставка не считается транзакцией БД.
Не отправлять просроченный push после прочтения / потери актуальности события.
Collapse только в рамках согласованной группы, не между чужими комнатами / аккаунтами.
Записывать event_id, recipient/device registry ID, provider message ID, attempt, timestamps и safe error code.
Разделять created / queued / provider accepted / device received / displayed / opened / read ACK.
APNs/FCM/OneSignal acceptance не является физическим PASS.
Ошибки и ограничения ОС отражать явно; отсутствие device receipt не заменять догадкой.

## 14. Автоматическая регрессия
Проверить формулу unread, дедуп сообщения и его уведомления, room boundary, stale ACK, смену аккаунта, logout race.
Проверить deep link до auth-ready, после logout и при запрете доступа.
Проверить outbox retries, TTL, worker recovery, stale token, per-device partial success.
Проверить foreground suppression, wrapped OneSignal payload, targeted removal, один FCM handler.
Запустить существующие связанные тесты; новые тесты добавлять на реальный найденный дефект.
Для новой правки повторять затронутые проверки; не повторять весь зелёный набор без изменения.
Автотесты и симулятор не заменяют физическую матрицу.

## 15. Измерения и критерии 10/10
Основные состояния foreground-other, background, locked, swipe-recents: минимум три повторения на каждом устройстве.
Цели при стабильной сети и разрешениях: видимое новое сообщение / push до 5 с, сверка после подтверждённого чтения до 3 с.
Это приёмочные цели продукта, не гарантия APNs/FCM. Записать фактические значения каждого повтора и отклонения.
Основная матрица: ноль потерь, дублей, чужих переходов и необъяснимых unread в выполненном прогоне.
Все цифры соответствуют серверной формуле; после чтения очистка точечная.
События других комнат сохраняются; новый unread во время ACK не теряется.
iPhone, OPPO, Huawei имеют отдельный доказанный результат.
Нет открытых P0/P1 по push и связанных доступах.
Неподдерживаемый числовой OEM badge описан точно; для числовой приёмки на конкретном устройстве нельзя молча подставить точку.
При BLOCKED/FAIL одного обязательного устройства общий push 10/10 не ставится.

## 16. Артефакты и итоговый отчёт
Сохранить spec, матрицу CSV/Markdown, safe server audit и screenshots/video в QA evidence.
Строка результата: case_id, device/build/package/host, role, event_id, room_id, initial/final unread, initial/final badge, send/receive/open/read timestamps, status, evidence path.
Для каждого дефекта: reproduce, expected/actual, affected SHA/build, root cause или UNKNOWN, patch SHA, regression test, retest.
Статусы: PASS / FAIL / PARTIAL / BLOCKED / NOT TESTED.
Отдельно: код сохранён; APK/IPA собран; установлен; push отправлен; физически показан; прочитан; очищен.
Итог не скрывает блокеры и не переносит исторический PASS.

## Причина и изменение

`destination_message` повторяется в исходной очереди. Ключ из одного номера перезаписывал revision соседних записей и исчерпывал LIMIT 50 на уже просмотренных строках.

Новые таблицы `published_bridge_seen_v2` и `published_bridge_rejections_v2` используют уникальный `queue.id` исходной SQLite. Старые таблицы сохраняются. Неоднозначные старые ACK не копируются: свежие исходные строки проходят однократную пересверку через прежний идемпотентный outbox. Existing pending delivery, retry metadata и payload при создании v2 не изменяются. HTTP identity остаётся source_id/source_message_id/segment_id; новых API-схем нет.

Состояние v2 относится к той же исходной queue DB; замена/сброс исходной очереди не входит в scope. На первом запуске будет проход по всем подходящим строкам текущего TTL, по 50 за цикл; длительность догоняющего прохода ещё не измерена на реальной очереди.

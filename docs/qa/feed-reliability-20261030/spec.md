# Техническое задание: надёжная загрузка объявлений UrTruck

Версия 1.0 · 30 октября 2026 года

Статус: спецификация для реализации и приёмки. Документ сам по себе не означает, что изменения установлены на сервере.

## 1. Цель и границы

Обеспечить непрерывный приём разрешённых Telegram-объявлений, сохранение исходника целиком, показ найденных контактов, разделение грузов и свободных машин, восстановление после сбоев без потери сообщений и повторной массовой публикации.

Работы относятся к сборщику, обработке объявлений, отправке в Telegram, API и двум внешним лентам UrTruck. Авторизация, сделки, платежи, чаты, GPS, собственные грузы и рейсы пользователей не меняются этой задачей.

Правило хранения внешних лент: 10 суток от времени исходной публикации; после истечения 240 часов объявление исчезает из активной выдачи и счётчика. Это означает удаление из публичной ленты на 11-е сутки. Срок 30 дней для собственных грузов и машин — отдельное правило, не переносимое на внешние ленты.

Невозможно гарантировать отсутствие любых сбоев Telegram, сети или сервера. Обязательный результат — обнаружение остановки, сохранение очереди, ограниченные автоматические повторы, восстановление и понятный сигнал о проблеме.

## 2. Основные неизменяемые правила

1. Сначала надёжно сохранить полученное сообщение, затем разбирать и доставлять.
2. Исходный текст, порядок строк, цифры и контакты не переписывать и не сокращать. Структурированные поля — дополнение к оригиналу.
3. Ошибка распознавания маршрута, цены, кузова или телефона не является причиной потери объявления из подтверждённой группы UrTruck.
4. Отправка в Telegram и доставка в приложение имеют независимые состояния и очереди. Остановка одного направления не блокирует другое.
5. Повторный запуск, повторная доставка и восстановление данных не создают повторные карточки одного и того же сообщения/сегмента.
6. Счётчик отражает реальные доступные записи. Нельзя увеличивать его искусственно или добиваться количества копированием одинаковых карточек.
7. Один проблемный элемент не останавливает обработку остальных элементов, которые могут быть доставлены безопасно.

## 3. Источники и сохранение оригинала

Перед реализацией составить фактический реестр: идентификатор Telegram-чата, название, ссылка, роль источника или получателя, доступность, последний полученный и последний доставленный message_id. В реестр включить `@UrTruck_obyavleniya`, `@UrTruck_UT` и остальные уже разрешённые источники. Не определять роль чата только по похожему названию.

Для подтверждённой группы `@UrTruck_obyavleniya` разрешён приём объявлений без обязательного наличия распознанного маршрута, телефона или цены. Telegram-события входа участников и прочие служебные события не превращаются в грузовые карточки. Классификация внешних источников должна быть отдельно описана в реестре.

Для каждого сообщения сохранять:

- chat_id, message_id, дату оригинальной публикации и дату получения;
- полный текст и подпись к медиа в исходном виде, Telegram entities и доступную ссылку на источник;
- идентификаторы доступных вложений и альбома, сведения об изменении сообщения;
- контрольную сумму оригинального содержимого, версию обработчика и результат каждого этапа доставки;
- связь всех полученных карточек с одним исходным сообщением.

Исходник не заменять результатом парсера. При редактировании сохранять новую ревизию с возможностью установить, что именно изменилось. Повторное чтение сообщения обновляет его, а не создаёт новый источник.

На всём пути проверить ограничения длины: Telegram → локальное хранилище → очередь → HTTP → API → база → ответ клиенту → раскрытая карточка. Недопустимы молчаливые срезы строки. Если размер превышает допустимый предел, сообщение сохраняется, получает диагностическую причину и обрабатывается отдельным способом; хвост не отбрасывается.

При публикации текста длиннее допустимого для Telegram использовать согласованный способ: несколько пронумерованных частей с сохранением порядка и связи. Состояние доставки хранить для каждой части; после сбоя не пересылать уже подтверждённые части. Перенос телефона в шапку не заменяет сохранение конца оригинала.

## 4. Телефоны и другие контакты

Искать контакты во всём оригинале: начале, середине, конце, подписи к медиа и явно переданных контактных данных сообщения. Поиск выполняется до разбиения на отдельные заявки.

Поддержать международные и местные номера, в том числе 7–8 цифр, номера без плюса, пробелы, скобки, дефисы, Unicode-цифры и несколько номеров. Сохранять написание номера для отображения. Отдельная нормализованная форма используется для сравнения и копирования, без придумывания кода страны или недостающих цифр.

Числа, явно обозначающие цену, дату, вес, объём, количество машин, номер заявки или банковские реквизиты, не объявлять телефоном автоматически. Неоднозначное число остаётся в полном тексте; сомнительный контакт можно показать с обозначением необходимости сверить его с оригиналом.

Правила принадлежности:

- номер внутри отдельной заявки показывается у этой заявки;
- явно общий контакт всего сообщения показывается у заявок этого сообщения;
- если в посте несколько номеров и их принадлежность неясна, показывать их как «Контакты исходного объявления», сохраняя полный текст для сопоставления;
- запрещено брать номер из соседнего сообщения, чужой заявки или закрытого профиля для заполнения пустого поля.

Если контакт есть только на изображении, исходное вложение должно быть доступно пользователю. Распознавание изображения — отдельная обработка: сомнительные цифры не выдаются как подтверждённый номер.

Сообщение «Телефон не найден в исходном объявлении» допустимо после проверки полного доступного оригинала. Если оригинал неполный или обработка не завершена, состояние должно обозначать именно это. Отсутствие телефона не скрывает объявление.

## 5. Карточка и сообщения с несколькими заявками

Основной порядок карточки:

1. Откуда → куда.
2. Цена и валюта либо «Цена не указана»/«Договорная».
3. Телефоны и другие найденные контакты с копированием.
4. Краткие параметры, дата исходной публикации и доступная ссылка на источник.
5. Полный оригинальный текст по кнопке «Показать полностью».

«Показать полностью» раскрывает действительно весь исходный пост, включая контактный хвост. Сворачивание влияет только на отображение. Длинный текст прокручивается до конца; кнопки доступны, приложение не зависает. Одинаковые данные API должны одинаково отображаться на поддерживаемых клиентах.

Сообщение можно разделить на карточки, когда границы заявок определены. Маршрут, цена, кузов и локальный контакт извлекаются из соответствующего блока. Полный общий оригинал остаётся доступен у каждой карточки. Нельзя переносить цену первого маршрута на остальные.

Если безопасное разбиение невозможно, сохранять целое объявление одной карточкой с понятным указанием нескольких направлений. Не создавать несколько внешне одинаковых карточек без различимого содержания. Идентификаторы сегментов должны сохранять корректную связь при редактировании исходного поста.

## 6. Грузы и машины

Лента грузов предназначена водителям: «груз готов», «нужна машина», «нужен тент/реф», «требуется перевозка» и аналогичные сообщения о грузе.

Лента машин предназначена грузоотправителям: «машина свободна», «ищу груз», «машина готова», «пустой», «заберу груз», «свободная фура» и аналогичные предложения транспорта.

Классификация учитывает смысл фразы, отрицания и контекст. Само слово «машина» не означает предложение свободного транспорта. Проверить используемые в источниках русские, узбекские и казахские формулировки, транслитерацию и распространённые сокращения.

Для смешанного сообщения выделять подтверждённые блоки по типу. Если тип остаётся неопределённым, сохранить исходник и доставить его в видимый раздел «Тип не определён» внутри внешних объявлений. Не приписывать такой карточке подтверждённую категорию и не прятать её в недоступную пользователю очередь. Конкретное расположение этого состояния согласовать в макете до изменения интерфейса.

## 7. Исправление уже загруженных карточек

Новые правила должны применяться и к существующим активным карточкам, а не только к будущим сообщениям.

1. Снять исходные показатели: количество карточек с контактами, без контактов, без полного оригинала и с ошибками обработки.
2. Найти первоисточник по chat_id/message_id. Использовать сохранённый полный оригинал; при необходимости повторно получить доступное исходное сообщение.
3. Повторно извлечь контакты и поля, обновить связанные карточки с сохранением их идентичности, закладок, дат и ссылок.
4. Не возвращать самостоятельно закрытые, скрытые владельцем или просроченные записи в активные.
5. Не обновлять дату публикации ради продления жизни старого объявления.
6. Выдать отчёт: сколько исправлено, сколько не требовало изменений, сколько осталось без доступного источника или без телефона в оригинале.

Восстановление выполнять возобновляемыми пакетами с журналом изменений и предварительным просмотром результата. Сведения из старых карточек не стирать при ошибке получения оригинала.

## 8. Очереди, сбои и контроль работы

У каждого направления доставки должен быть явный жизненный цикл: ожидает → выполняется → подтверждена; отдельно — повтор после ошибки и неопределённый результат отправки. Захват элемента имеет ограниченное время действия.

При зависшей отправке сначала сверять результат с Telegram. Подтверждённое сообщение не пересылать заново. Если требуется повтор, использовать прежний ключ идемпотентности и учитывать срок его действия у внешней системы. Неподтверждённый результат нельзя произвольно считать успешным или неуспешным. Сверка имеет ограниченную длительность; проблемная запись не блокирует независимые объявления.

Обработать: потерю сети, перезапуск процесса/сервера, HTTP 429/5xx, FloodWait, недоступность API, ошибку одного сообщения, потерю сессии, отсутствие прав публикации и заполнение диска. При временной ошибке — повторы с увеличением паузы; при ошибке доступа — сигнал оператору. Самовосстановление не должно обходить ограничения Telegram или менять права доступа.

Период проверки очереди приложения — целевой 2 секунды. Целевой интервал отправки в Telegram при готовой очереди — 2–3 секунды только при допустимости текущими ограничениями Telegram. В последней подтверждённой проверке 29 октября фактическая настройка Telegram составляла 15 секунд; перед изменением измерить её заново. Таймер опроса и реальную скорость публикаций показывать отдельно.

Контроль не реже одного раза в минуту измеряет время последнего входящего сообщения, последней успешной доставки в каждом направлении, возраст старейшего ожидающего элемента, число повторов, паузу Telegram и последний прогресс обработчика.

Сигнал об остановке: есть готовая очередь, нет установленной внешней паузы и нет успешной доставки более 120 секунд. Выявление и отправка сигнала — не позже следующего контрольного цикла. Пустая очередь не является аварией. Для FloodWait показывать причину и время допустимого возобновления.

Использовать один ограниченный цикл восстановления: сверка состояния → безопасное возобновление → подтверждение прогресса. Исключить бесконечные перезапуски. Канал уведомлений и получатель должны быть явно настроены и проверены. Повторные одинаковые сигналы объединяются; восстановление подтверждается отдельным событием.

## 9. Фильтры, счётчик, сохранённое

Распознавание полей не должно удалять исходник. Сортировка по цене не исключает все карточки без цены: они располагаются после карточек с известной ценой. Смешанные валюты нельзя сравнивать как одинаковые числа; использовать согласованное правило и обозначать его пользователю.

Счётчик и выдача используют одинаковые условия доступа, категории, срока жизни и фильтров. Общий счётчик ленты явно отличается от количества найденных по фильтрам. Проверить одинаковость результатов на iOS и Android при одном аккаунте, параметрах и версии данных.

Меню фильтра закрывается отменой, нажатием вне меню и стандартным жестом/кнопкой назад там, где они поддерживаются. «Сброс» очищает фильтр и не служит обязательным способом выхода. Переход к другому фильтру не блокируется открытой клавиатурой. В кузове остаётся свободный ввод.

Закладки сохраняются при обновлении исходника и повторной обработке. Ошибка загрузки сохранённых имеет сообщение и повтор, а не бесконечный индикатор. Регрессионно проверить эти существующие требования; исправления несвязанных дефектов проводить отдельными небольшими изменениями.

## 10. Обязательная приёмка

| Сценарий | Требуемый результат |
| --- | --- |
| Телефон в начале, середине и конце | Найден и доступен сверху; исходник полностью совпадает |
| Местный номер, разделители, Unicode-цифры | Поддерживаемые варианты распознаны без добавления цифр |
| Цена/дата/вес похожи на телефон | Не превращены в подтверждённый телефон |
| Несколько маршрутов и общий телефон | Контакт сохранён, цены не перепутаны, полный пост доступен |
| Несколько маршрутов с разными контактами | Локальные контакты привязаны правильно; неоднозначность обозначена |
| Очень длинный пост и телефон в конце | Конец текста и телефон присутствуют после каждого этапа |
| Телефон только в изображении | Вложение доступно; результат распознавания не выдуман |
| Источник действительно без телефона | Карточка доступна, отсутствие обозначено честно |
| Повтор импорта и перезапуск | Нет дублирования карточек/подтверждённых отправок |
| Редактирование исходника | Обновление данных с сохранением закладок и связи с источником |
| Зависший элемент, сбой API или Telegram | Сохранение данных, независимость направлений, восстановление и сигнал |
| Истечение 10 суток | Карточка и её вклад в счётчик исчезают синхронно |
| Груз и свободная машина | Попадают в соответствующие ленты |
| Фильтры, цена, сохранённое | Нет потери результатов, блокировки интерфейса или вечной загрузки |

Для каждого поддерживаемого формата нужен воспроизводимый пример и ожидаемый результат. Дополнительно проверить не менее 50 реальных объявлений из разрешённых источников, включая все доступные примеры жалоб владельца. Чужие телефоны и полный текст не выводить в общие технические логи; подробные материалы проверки хранить с ограниченным доступом.

Сверять оригинал посимвольно, а контакты — по принадлежности и числу найденных номеров. Достижение 100% распознавания на выбранной выборке не объявлять гарантией для всех будущих сообщений.

Серверная приёмка: минимум 60 минут наблюдения после установки, включая контролируемый перезапуск и временную недоступность одного направления в тестовом окружении. При готовой очереди не должно оставаться необъяснённых остановок. Затем сутки наблюдения по метрикам для подтверждения устойчивости.

Если меняется клиентский интерфейс, провести отдельную проверку на физическом Android и iPhone. Серверные тесты не заменяют проверку приложения. Отсутствующая платформа получает статус «не проверено».

## 11. Порядок реализации и откат

1. Зафиксировать актуальные ветку/SHA, настройки сервисов, версии клиентов, фактическую цепочку источников и проблему на конкретных сообщениях.
2. Сохранить резервные копии затрагиваемых данных и настроек. Проверить возможность восстановления до массовой обработки.
3. Составить перечень файлов и минимальных изменений: сохранение оригинала → контакты → формирование ответа → отображение → восстановление старых данных → устойчивость очередей. Выполнять отдельными проверяемыми шагами.
4. Подготовить изменения через PR, выполнить необходимые проверки на точном SHA. Сохранить совместимость со старыми клиентами API.
5. Установить в QA2, прогнать матрицу и сверить реальные карточки с источниками. Исправить старые записи пакетами после проверки предварительного отчёта.
6. Подтвердить показатели до/после и стабильную доставку. Расширять запуск только после успешной приёмки предыдущего этапа.

Откат кода и настроек должен возвращать предыдущую рабочую версию. Откат восстановленных карточек выполняется по журналу затронутых записей; нельзя заменять всю базу старой копией и терять новые сообщения, поступившие после резервирования. Откат не запускает повторную отправку уже доставленных Telegram-сообщений.

Production-развёртывание и новая магазинная сборка оформляются отдельно после готового результата QA2. Серверная правка может исправить данные в существующем приложении; изменение порядка элементов интерфейса может потребовать обновления клиента. Это определить по проверке совместимости, не обещать заранее.

## 12. Что считается выполнением

Задача закрывается по отчёту с точным установленным SHA, подтверждённой сохранностью оригиналов, результатами распознавания и восстановления, правильной классификацией, проверенными очередями и уведомлениями, показателями наблюдения и результатами устройств при изменении UI.

В отчёте обязательно указать оставшиеся случаи без телефона и причины: нет в оригинале, недоступен источник, только изображение или нераспознанный формат. Их нельзя скрывать общей фразой «всё исправлено».

Рабочая служба, HTTP 200, зелёный CI или рост счётчика по отдельности не доказывают выполнение ТЗ. Критерий — новые и восстановленные объявления доходят с полным оригиналом, имеющиеся контакты доступны, а сбои обнаруживаются и обрабатываются по установленным правилам.

Три уровня доказательств вести отдельно:

1. **Код:** конкретный SHA, реально используемый путь, тест и его результат.
2. **Сервер:** фактический runtime, конфигурация, API-контракт, событие и безопасный лог.

## 5. P1: исправить рост поля сообщения на iPhone

Требуемое поведение при обычном масштабе текста: пустое поле компактное; по мере ввода видимая высота растёт для 1, 2, 3, 4 строк; начиная с пятой высота ограничена четырьмя строками, текст прокручивается внутри вверх, курсор остаётся видимым. Это относится к Enter и автоматическому переносу длинного текста.

Аудитировать TextInput, `onContentSizeChange`, `normalizeComposerHeight`, управляемую height, iOS/Android padding, lineHeight, min/max, scrollEnabled, родительский inputShell, клавиатуру/safe-area, font scaling, восстановление черновика и запоздавшие callbacks. Проверки:

- 1→2→3→4→5→8 строк; затем удаление обратно до 1 и очистка;
- длинная строка без Enter, вставка 4/8 строк, emoji, RU/ZH/EN/KK, китайская IME-композиция;
- быстрый набор/удаление, перемещение курсора, выделение/вставка, autocorrect;
- показ/скрытие клавиатуры, уход/возврат, черновики двух разных комнат, восстановление приложения;
- успешная отправка сбрасывает высоту; при ошибке отправки введённый текст сохраняется;
- кнопки «+», отправки и голоса доступны, не перекрывают текст; последние сообщения и шапка не прыгают;
- крупный системный шрифт не обрезает текст: политика ограничения учитывает фактический lineHeight.

## 6. P1: push, unread, badge и очистка

Проследить единое событие от бизнес-операции до outbox, worker, выбора recipient/device/provider, APNs/FCM/Expo ответа, ОС телефона, счётчиков приложения и действия при открытии. Проверить, что sender не получает собственный push и другой аккаунт не получает уведомление после смены сессии.

Серверный аудит:

- `chat:ROOM` отделяет комнаты от уведомлений сделок;
- idempotency outbox, повторный worker/restart, transient retries, permanent errors, stale/disabled tokens, receipts, дедупликация;
- APNs production bundle/topic, production environment, effective configuration, payload alert/sound/badge и deep link; секреты проверять по наличию и безопасным признакам;
- FCM-обработчик единственный в **фактическом merged manifest** кандидата; совместимость Expo сохранена;
- badge считается при отправке, а не только при создании задания; устаревшее задание не возвращает старую цифру после чтения;
- наблюдаемые provider ошибки связываются с event/outbox/device без вывода токена. Старые dead события не переотправлять массово.

Физическая матрица на iPhone/Huawei/OPPO:

| Состояние получателя | Что проверить |
| --- | --- |
| Открыта нужная комната | Сообщение видно один раз; unread/read и презентация соответствуют текущему контракту |
| Открыт другой экран/комната | Уведомление о правильной комнате; её unread растёт, другая комната сохраняется |
| Приложение в фоне | Системная доставка, звук/вибрация при разрешённых настройках, правильный badge |
| Экран заблокирован | Lockscreen, доставка, счётчик, переход после разблокировки |
| Убрано из последних | Зафиксировать точное действие и поведение ОС отдельно от обычного background |
| Системный force-stop Android | Не обещать доставку до повторного запуска; проверить восстановление после запуска |
| Нет сети → сеть вернулась | Нет потерь/дублей; корректное восстановление unread/badge |
| Уведомления запрещены / Focus | Приложение не падает; ограничения ОС показаны отдельно от server failure |

Для iOS отдельно записать разрешения Alerts/Badges/Sounds, баннеры/lockscreen, Focus/Sleep и Scheduled Summary. Приложение не может гарантировать верхний баннер вопреки настройкам ОС; показ баннера нужно проверить при согласованных разрешённых настройках. Скриншот badge 3 закрывает только наблюдение одной цифры, не всю матрицу.

Контрольные последовательности:

1. Комната A: три новых сообщения → unread 3 → native badge согласно контракту → открыть A → прочитать → её unread 0.
2. Комната B и непрочитанное событие сделки: оставить уведомления; чтение A не удаляет B/сделку и не обнуляет весь счётчик.
3. Новое сообщение приходит одновременно с чтением A: оно не теряется, запоздавший read/badge ответ не стирает новый unread.
4. Прочитать с другого устройства того же аккаунта: последующая синхронизация согласована, stale notification не возвращает уже прочитанный счётчик.
5. Нажать push из cold start/background: открывается нужная доступная комната и собеседник; после logout или истёкшей сессии нет обхода доступа.
6. Сменить аккаунт: токен и очередь не раскрывают данные прежнего аккаунта, старый запрос не обновляет новую сессию.
7. Проверить новое предложение, принятие/отклонение и все реализованные важные события FSM/GPS. Отсутствующее предусмотренное событие отметить как GAP, не считать проверенным.

Huawei обновлять штатно поверх с сохранением данных, когда владелец введёт Huawei ID. OPPO проверять именно для `com.urtruck.app`, включая разрешение badge в launcher. На каждом устройстве фиксировать до/после, точную цифру, уведомления в шторке и счётчики внутри приложения.

## 9. Логика ролей, предложений, сделки и общего состояния

Проверить не имена, а server user IDs, роли и membership. Один и тот же пользователь с двумя ролями должен видеть корректный интерфейс и доступ. Имя serik не заменяет проверку идентификатора.

Сценарии на изолированных тестовых данных:

- shipper создаёт/публикует груз → driver видит его и корректные условия;
- driver отправляет одну ставку → owner видит правильную машину, автора, цену, валюту и дату;
- принятие создаёт одну сделку и комнату; обе стороны входят в неё; pending/отклонённая ставка не открывает закрытый чат;
- конкурентное принятие двух ставок, повторный тап/запрос и потеря ответа не создают второго победителя/комнаты/push;
- реализованная FSM соответствует ролям: водитель отмечает доставку, shipper подтверждает получение; третья сторона не меняет статусы;
- международная граница проверяется по текущему канону, без выдуманных переходов;
- оба клиента после refresh/relogin/offline recovery видят один статус и следующее действие; архив/отмена/истечение не оставляют неправильную активную карточку;
- сумма и валюта сохраняются во всех представлениях, не смешиваются с переводом интерфейса;
- лог событий сохраняет actor, предыдущее/новое состояние и время; UI не считается источником истины;
- push/deeplink, list, detail и map открывают одну и ту же сделку.

Если найдена гонка или расхождение состояний — воспроизвести порядок запросов и добавить интеграционный тест. Не «чинить» его прямым редактированием production БД.

## 10. Безопасность, авторизация, документы, GPS и карта

**Доступы:** на тестовых пользователях проверить owner/counterparty/third party/anonymous для deal, room, messages, STT, переводов, attachments, private URLs, GPS, notifications/badge. Подмена ID не раскрывает содержимое и не создаёт побочный эффект. Ответы 401/403/404 оценивать по принятому контракту; важно отсутствие данных/изменений. Чувствительные телефоны и документы не должны попадать в публичный feed/log.

**Авторизация:** существующие Google/Apple/email/OTP сценарии, logout, истёкший токен, возвращение с background, две роли, смена аккаунта и registration push token. Не внедрять новые способы входа. Проверить отсутствие production bypass/test codes, опасных fallback и токенов в URL; защиту повторного использования OTP/rate limits проверять в безопасном окружении.

**Документы/фото:** upload/view/download у обеих сторон, PDF/изображение, MIME/размер, отмена/retry, offline, повторная отправка без дублей, lifecycle viewer и закрытие. Подписанная ссылка не должна переживать разрешённый срок/доступ; third party не читает файл. Опасные форматы и негативные тесты — изолированно.

**GPS/карта:** runtime permissions запрашиваются после «Начать рейс» с актуальным disclosure; все входы используют DealWorkspaceRoute и permission gate. До начала рейса нет tracking/закрытых координат. После разрешённого старта backend и обе стороны согласованы; карта встроена в UrTruck. Проверить реальные маршрут/позицию/свежесть, foreground/background/locked, 15/30 минут, stationary/movement, GPS OFF→ON, denial, offline FIFO/recovery. Не обещать tracking после системного force-stop. Завершение/отмена останавливают tracking. Third party не читает историю. Серый пунктир не считать дорожным маршрутом.

Проверять существующее платежное/документное состояние там, где оно связано со сделкой, но не проводить реальные финансовые операции. Общий аудит выявляет gaps; он не разрешает автоматически внедрить новые платежи, MapKit или изменить FSM.

## 13. Исправления и один согласованный кандидат

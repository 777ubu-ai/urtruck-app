# FEED-13 — диагностика и статус кандидата

Срез этого отчёта: локальная ветка `fix/feed13-review-sql-throughput`, основана на установленном кандидате QA2 `4d3525ff8d29d0204ed76aff49306c326972defb`. Изменения ниже локальные и пока не установлены. Очереди и пользовательские данные не очищались.

## Подтверждённая причина низкой скорости incoming

Логи двух циклов установленного QA2 показывали `source_scan_ms=146403` и `137507` при выборе пачек на 50 строк. Разбор занимал 1139–1222 мс, запись outbox — 354–378 мс, flush API — 2712–2910 мс. Значит, подтверждённый доминирующий этап — выборка исходников.

В `IncomingQueueBridge` подсказка свободной машины выполнялась как Python SQLite UDF в условии SQL по большой истории. `LIMIT` ограничивал число выбранных строк, но не число вызовов UDF. Локальный синтетический benchmark на 100 000 строк с двумя предложениями машины сравнивает прежний путь (100 000 классификаций, медиана 2243 мс) с ограниченным окном (500 классификаций, медиана 11.863 мс; около 189× быстрее в этой синтетической конфигурации). Это локальный benchmark, не обещание такого ускорения на QA2.

В кандидате классификация машин ограничена окном из 500 последних неразобранных исходников; старые исходники продолжают поступать через индексированный oldest-first путь. Добавлен регрессионный тест границы окна. После установки нужно измерить реальную скорость и проверить, что старые предложения машин не голодают.

## SQLite и `database is locked`

На QA2 ранее зафиксированы два `database is locked` у `import_records` в `11:59:24.465Z` и `11:59:24.488Z`; задача очистки API записала `purged=116` около `11:59:31Z`. Близость по времени — сильная корреляция, но не окончательное доказательство, что именно очистка удерживала блокировку.

В таблице аудита не было индекса по `item_id`, хотя удаление истории очистки выполнялось по этому полю. Запрос очистки также объединял датированные и недатированные записи через `OR` и `COALESCE`, затрудняя использование сортированных индексов. Добавлены индексы и разделены выборки по датированным/недатированным записям; импорт и очистка теперь логируют длительность безопасно, без содержимого объявлений. В адресных тестах конкурентные импорт и очистка сохранили ожидаемые записи.

Установка ещё не выполнена, поэтому отсутствие повторного HTTP 500 на QA2 не подтверждено. После deploy проверить журналы, ожидание SQLite lock и согласованность источника/API.

Для 24 сегментов с заполненными основными полями parser сообщал неоднозначную/невалидную структуру маршрута. Это не ручная проверка полного исходного сообщения, охват каждого настроенного источника отдельно не подтверждён, поэтому требование ручной разметки минимум 200 сообщений ещё НЕ выполнено.

## Установлено по исходникам

- `POST /api/v1/market/cargos` проходит через backend `require_active_level(1)`, затем `_require_role(user, ("client",), "разместить груз")`. Запрет водителю — штатная защита; она сохранена.
- При отказе backend возвращает HTTP 403 и стабильный `ROLE_NOT_ALLOWED`, а также каноническую роль из запроса. Старое поле `message` остаётся для обратной совместимости.
- `marketAPI.createCargo()` превращал `detail.message` в строку и терял код; `CreateCargoScreen` показывал эту строку напрямую. Поэтому известный отказ отображался по-русски независимо от языка клиента.
- Стек приложения регистрирует `CreateCargo`, а экран использует navigation role с fallback `client`; это presentation context, не источник полномочий. Авторитетная проверка остаётся на API. В текущем пользовательском случае фактическую роль установить нельзя без точного user ID и свежего `/register/me`/`/users/me` либо безопасного ответа запроса.
- Регистрация сохраняет только каноническую роль `driver`/`client`; общий PATCH профиля нормализует alias `shipper` в `client`. AuthContext обновляет локальный профиль по `/register/me`. Конкретное расхождение этих источников у целевого аккаунта пока не подтверждено.

## Изменение

- `marketAPI.createCargo()` теперь сохраняет стабильный `errorCode` в клиентском результате, не меняя payload, HTTP-ответ или backend-права.
- Новый `cargoPublishErrorMessage()` локализует только `ROLE_NOT_ALLOWED`; ошибки старого сервера и другие ответы продолжают показывать прежнюю строку/общую локализацию.
- Добавлены отдельные RU/KK/ZH/EN сообщения. Китайский текст объясняет ограничение текущего типа аккаунта и путь проверки; он не предлагает менять роль без подтверждения.

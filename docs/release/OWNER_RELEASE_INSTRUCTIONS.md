# UrTruck — обязательная инструкция выпуска

Решение владельца от 14.11.2026. Читать перед любой подготовкой сборки, QA2-deploy, TestFlight, Google Play Internal, App Store или production. Это постоянные правила; текущие SHA, версии и результаты хранить отдельно в checkpoint. Более новое явное решение владельца имеет приоритет.

## 1. Исходник и окружение

- Прочитать AGENTS.md, эту инструкцию, канон проекта и текущий checkpoint.
- Установить актуальные ветку, SHA, незакоммиченные изменения и backend runtime. Сохранить чужую работу. Зафиксировать preflight: scope, known-good, проверки и откат.
- У каждой сборки должны быть известны исходный SHA, API, версия, номер, package/bundle ID, подпись и SHA-256 файла.
- Не собирать старую ветку и не путать QA2 с production. Различия тестовой и боевой баз объяснять, а не маскировать сменой API.

## 2. Сохранность данных и объявления

Без отдельного разрешения владельца запрещены удаление, очистка, массовая перезапись и замена аккаунтов, грузов, рейсов, машин, предложений, сделок, чатов, файлов, истории и backup. Истечение срока показа не разрешает удаление записи.

Активные собственные грузы и рейсы продлеваются каждые 30 суток с прежними ID, владельцем, маршрутом, ценой, контактами и историей. Проверять фактическую политику, миграции и scheduler в окружении. Отменённые, снятые, занятые и завершённые объявления автоматически не возвращать в активные; старые истёкшие ставки не оживлять. Архив и историю сохранять по правам доступа.

Внешние грузы показываются 30 дней, внешние машины — 10 дней. Не применять эти сроки к собственным объявлениям. Каталог перевозчиков — отдельный источник, срок удаления по аналогии ему не назначать.

Deploy не должен заменять базу, файлы или настройки чужого окружения. Миграции и rollback должны сохранять новые пользовательские данные. Production в QA2 вслепую не копировать.

## 3. Ленты, счётчики и скорость

Отдельно сверять пользовательские грузы, рейсы/машины, внешние грузы, внешние машины и каталог водителей/перевозчиков. Для каждого источника указывать время, окружение, права, фильтры, активные записи и историю.

- Сравнивать базу → API → интерфейс в одинаковых условиях. Не подменять общий итог размером страницы, не прошивать числа в интерфейс.
- Пагинация должна выдавать разрешённые записи без дублей и пропусков, сбрасываться при смене фильтра/роли. Кэш разных аккаунтов не смешивать.
- Ранее восстановленные объявления сохраняют ID, владельца, статус и связи со сделками.
- Счётчик получать до открытия внешней ленты; не загружать тысячи карточек ради подсчёта.
- Не оставлять бесконечные «…», несколько несогласованных загрузчиков и молча пустые экраны. Различать загрузку, пустую выдачу, отсутствие доступа и сетевую ошибку; предоставлять понятный повтор.
- Измерять API, счётчик и первую страницу до/после. Отсутствующий замер честно обозначать. Увеличение числа завершёнными/чужими записями не является исправлением.

Числа из старых отчётов — исторические срезы, не обязательные постоянные значения. Разница QA2/production сама по себе не доказывает потерю данных.

## 4. Вход и регистрация

Решение владельца: обязательный вход, пробный/гостевой рабочий режим убрать. Без действующей сессии — понятный вход/регистрация через поддерживаемые Google, Apple и почту; с сессией — сразу приложение нужной роли. Не создавать дубликат вместо входа. Автомобиль при регистрации водителя необязателен.

Прямые ссылки не обходят вход. Временная ошибка сети не удаляет сессию. Обновление поверх приложения сохраняет аккаунт и данные. Наличие вкладок не доказывает авторизацию: проверить доступ к данным правильного пользователя. Требование документа не означает, что оно уже внедрено: подтверждать точный кандидат.

## 5. Push и защищённые функции

Проверять событие → outbox → провайдер → устройство → нужный чат/сделка; фон, баннер/звук при разрешённых настройках, бейдж иконки, «Сделки», вкладки и карточки, изменение после прочтения, отсутствие дублей и восстановление очереди после временной ошибки авторизации. Ответ провайдера не доказывает получение устройством.

244 старых удерживаемых push-события не выпускать. Тестовые сообщения реальным пользователям не отправлять. Проверять регистрацию устройства, FCM/APNs и актуальность ключей без вывода секретов.

Не ломать FSM сделки, роли, чат, повторы сообщений, документы, фото, голосовые, карту, согласованный режим GPS и локализацию RU/ZH/EN/KK. Участникам доступны разрешённые файлы, постороннему — отказ; сравнивать байты/хеши. Старые подписанные ссылки не считать отозванными без доказательства. GPS-режим сверять с последним решением владельца и фактическим manifest, не переключать попутно.

## 6. Проверки и магазины

Проверять связанные backend/API regression, frontend tests/lint/typecheck/build, Playwright/Maestro и реальные устройства для затронутых сценариев. Проверить обе роли, обновление, холодный запуск, плохую сеть и повторные нажатия. Не повторять успешные проверки без причины; PASS старого SHA/бинарника автоматически не переносится на новый. FAIL/BLOCKED/NOT RUN не скрывать.

Перед сборкой заново читать занятые версии и номера в App Store Connect/Play. Закрытую Apple серию повторно не использовать: загрузка 1.0.15(131) была отклонена ITMS-90186/ITMS-90062. Актуальную открытую версию определять свежей проверкой, не по этому примеру.

Проверять идентичность, версию, номер, API и подпись внутри готового бинарника. QA2-сборки с com.urtruck.app заменяют основное приложение: не устанавливать поверх рабочей сессии владельца без его решения; отдельный тестовый пакет/устройство предпочтителен. Существующие устройства не очищать и из аккаунтов не выходить.

После загрузки Apple проверить обработку VALID, статус внутреннего тестирования и наличие сборки в нужной группе. Проверить письма Apple об ошибках. В Google Play проверить фактическую версию, трек и статус. Успешный EAS Submit/GitHub Actions не означает доступность тестеру. Выдать ссылку, номер и инструкцию установки; не утверждать проверку конкретного Apple/Google-аккаунта без доказательства.

## 7. Разрешения и независимый reviewer

Независимый GitHub approval, назначение arbeiterschaft02-prog или другого отдельного reviewer НЕ являются обязательным условием продолжения. Не создавать этот блокер повторно. PR-процесс, инженерная проверка, CI, точный SHA и реальные технические ограничения сохраняются. Защиту доступа GitHub и магазинов не обходить.

Уже выданные разрешения действуют в согласованном объёме. Повторно их не запрашивать. Если разрешения ранее нет: production deploy/публичный выпуск, удаление данных и новые расходы отдельно согласовать. Разрешение тестовой загрузки не означает разрешения боевого выпуска.

## 8. Отчёт и продолжение

Сохранять checkpoint: что изменено, что проверено/не проверено, сравнение данных и причины различий, замеры, commit/PR/CI, backend SHA, версии/номера/SHA артефактов, фактические статусы магазинов и следующий шаг. Не хранить секреты и пользовательские данные в отчётах.

До боевого выпуска устранить регрессии принятых функций. Технический успех сборки не заменяет доказательство поведения продукта.

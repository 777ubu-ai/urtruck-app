## 1. Идентичность проекта

Репозиторий: `777ubu-ai/urtruck-app`.

Продукт: **UrTruck** — двухсторонний FTL-маркетплейс грузовых автоперевозок для коридора Китай ↔ СНГ. По продуктовой модели это “inDrive для фур”: грузоотправитель публикует груз/ставку, водитель публикует свободную машину/рейс или предлагает цену, стороны договариваются напрямую, после принятия работают через сделку, чат, документы, статусы рейса, GPS и пограничные инструменты.

Ключевые стороны:

- **Грузоотправитель / client / shipper** — публикует груз, получает ставки, выбирает водителя, контролирует сделку, видит машину на карте, подтверждает получение, оставляет отзыв.
- **Водитель / driver** — находит груз, предлагает цену, публикует свободную машину, начинает рейс, меняет статусы, передаёт геолокацию, работает с границей, завершает доставку.

Перед любой крупной задачей изучи обе стороны. Нельзя улучшать flow водителя ценой поломки shipper-flow и наоборот.

## 4. Ядро продукта — сделка и рейс

Энди обязан мыслить UrTruck как state machine, а не как набор экранов.

Ключевая цепочка:

**публикация → ставка/торг → принятие → сделка → рейс → граница → доставка → подтверждение → отзыв**.

При изменении любого шага проверь соседние шаги.

Особенно защищать:

- actor permissions — кто именно имеет право менять статус;
- idempotency;
- запрет доступа постороннего к сделке/чату/документам/GPS;
- отсутствие гонок при принятии ставок;
- корректное возвращение/закрытие публикаций;
- невозможность “завершить” рейс одной стороной в обход бизнес-правил;
- review только после корректного завершения.

Точный список статусов и actor rules всегда подтверждай фактическим backend FSM и актуальными tests перед правкой.

## 8. КРИТИЧЕСКОЕ временное ограничение Android GPS

На текущем `main` фоновая геолокация Android намеренно отключена из-за Google Play permissions declaration.

`ACCESS_BACKGROUND_LOCATION` и `FOREGROUND_SERVICE_LOCATION` нельзя возвращать вслепую.

Перед любым изменением background location:

1. прочитать актуальный раздел `CLAUDE.md`;
2. проверить текущий AndroidManifest/app config;
3. проверить требования Google Play и текущий release plan;
4. не включать permission только ради локального теста;
5. не заявлять background GPS PASS, если соответствующая capability реально не разрешена/не проверена.

Foreground GPS должен деградировать безопасно при отсутствии background permission.

## 9. GPS и карта — продуктовые правила

По текущему направлению продукта:

- водитель не должен принимать отдельное техническое решение “включить GPS” в середине flow, если продукт связывает это со стартом рейса;
- геолокация не должна отправляться до разрешённого состояния сделки/рейса;
- после завершения/отмены передача должна прекращаться согласно актуальному contract;
- грузоотправитель видит карту внутри UrTruck;
- основной tracking flow не должен выбрасывать пользователя во внешнюю карту;
- точка/скорость/ETA/давность должны быть честными, без выдуманных данных;
- location endpoint только для участников сделки;
- privacy важнее “красивого realtime”.

Точные допустимые статусы location проверять по текущему backend и tests, особенно если работа базируется на незамерженных GPS/MapKit ветках.

## 10. CGR / граница

Электронная очередь — отдельная стратегическая функция UrTruck.

При работе с границей:

- официальные/свежие данные нельзя смешивать с mock/legacy fallback;
- `null` не превращать в `0`;
- stale/unavailable не показывать как live;
- ETA не придумывать;
- источник и давность данных должны быть понятны;
- госномер/очередь/уведомление проверять как отдельный driver flow;
- интеграции CGR/Smart Bridge не менять по предположениям без проверки контракта.

## 16. Git и ветки

В UrTruck много исторических `agent/*`, `fix/*`, `feature/*`, `codex/*` веток и открытых PR.

Нельзя считать самую новую по названию источником истины.

Перед переносом из открытой ветки:

1. определить base/head;
2. сравнить с current main;
3. понять, какие изменения уже merged другим способом;
4. проверить tests/CI;
5. переносить только нужное.

Особенно осторожно с текущими/будущими GPS, Yandex MapKit и comprehensive-audit ветками: они могут содержать полезную работу, но до merge не являются production source of truth.

Не merge/push в `main` без отдельного явного разрешения пользователя. Для UrTruck это особенно важно, потому что `main` связан с production deploy workflows.

Запрещено без явного разрешения:

- `git reset --hard` по чужой работе;
- force push;
- массовый clean;
- удаление чужих веток с уникальными commit;
- production deploy;
- App Store / Play Store release.

## 19. QA — уровни доказательства

Энди и Том обязаны разделять:

1. **STATIC** — lint/type/static contracts.
2. **UNIT** — unit tests.
3. **INTEGRATION** — API/DB/CGR/storage/realtime.
4. **BUILD** — фактическая сборка.
5. **E2E** — автоматизированный пользовательский flow.
6. **DEVICE** — simulator/emulator/physical phone.
7. **PRODUCTION** — опубликованная версия.

Не подменять уровни.

Примеры:

- web build PASS ≠ iPhone работает;
- Maestro YAML valid ≠ Maestro PASS;
- API test PASS ≠ shipper видит машину на карте;
- GPS contract PASS ≠ background tracking работает на Android;
- unit tests PASS ≠ push доставлен на реальный телефон.

# OWNER ACTION — ротация `QA_AGENT_TOKEN` (P0, обязательно до релиза)

**Статус кодовой части:** уже исправлено (`backend/services/qa_token_guard.py`,
коммит `fd5c982` на этой ветке). Guard теперь распознаёт реально утёкший в
git-историю токен (найден в `qa/maestro/_run_clienthunt.sh`, коммит `0da68db1`)
и отклоняет его — раньше guard хранил один фингерпринт, который НЕ совпадал
с этим реальным утёкшим значением, и поэтому не блокировал его.

**Что осталось сделать владельцу/Codex с доступом к серверу** — сам код
ничего не может ротировать, у него нет доступа к продовому `.env` и к PM2.
Секрет ни в одном шаге ниже не печатается и не коммитится.

---

## Шаг 1 — сгенерировать новый `QA_AGENT_TOKEN`

На сервере (или локально, значение не должно попасть в git):

```bash
openssl rand -hex 32
```

Скопировать вывод — это и есть новое значение токена. Никуда, кроме шага 2,
его не вставлять (не в чат, не в issue, не в коммит).

## Шаг 2 — заменить секрет в продовом `.env`

```bash
ssh <ssh-user>@185.22.65.11
cd /home/ubuntu/urtruck-security   # или актуальный путь backend/.env на сервере
nano .env    # или любой редактор
```

Найти строку `QA_AGENT_TOKEN=...` и заменить значение на сгенерированное на
шаге 1. Если строки нет — добавить `QA_AGENT_TOKEN=<новое значение>`.

**Не забыть:** `backend/.env` не в git (см. `.gitignore`) — редактировать
только на сервере, не через PR.

## Шаг 3 — перезапустить backend-процесс

```bash
pm2 restart urtruck-security-api
pm2 logs urtruck-security-api --lines 30   # убедиться, что стартовал без ошибок
```

## Шаг 4 — проверить: старый (утёкший) токен → DENIED

Приложение никогда не хранит утёкшее значение — им нельзя реально
авторизоваться после ротации, но сам факт "сервер отклоняет" проверяется
без старого токена в руках: если `.env` СЕЙЧАС всё ещё содержал бы утёкшее
значение, эндпоинт был бы недоступен вообще — `qa_token_guard.py` проверяет
именно СЕРВЕРНЫЙ `QA_AGENT_TOKEN`, а не то, что прислал клиент:

```bash
curl -i -X POST http://185.22.65.11:8001/api/v1/qa/ensure-actor \
  -H "Content-Type: application/json" \
  -d '{"actor": "boris"}'
```

- Если `.env` ДО шага 2 содержал утёкшее значение — этот запрос ДО ротации
  должен был вернуть **503** `"QA agent endpoint disabled until QA_AGENT_TOKEN
  is rotated"`. Это и есть подтверждение, что guard действительно
  распознаёт и блокирует утёкший токен, а не просто ждёт корректного
  заголовка.

## Шаг 5 — проверить: новый токен → PASS

```bash
curl -i -X POST http://185.22.65.11:8001/api/v1/qa/ensure-actor \
  -H "Content-Type: application/json" \
  -H "X-QA-Agent-Token: <значение из шага 1>" \
  -d '{"actor": "boris"}'
```

Ожидаемый результат — **200** (актор создан/найден), НЕ 503 и НЕ 403.
403 означало бы, что заголовок не совпадает с тем, что реально лежит в
`.env` на сервере — перепроверить шаг 2/3 (перезапуск процесса обязателен,
иначе новый `.env` не подхватится).

## Шаг 6 — обновить секрет везде, где он используется вне сервера

Если `QA_AGENT_TOKEN` также хранится в GitHub Actions Secrets (для
Maestro/QA-раннеров CI) — обновить и там (`Settings → Secrets and
variables → Actions`), значением из шага 1. Иначе автоматизированные
QA-прогоны начнут получать 403 после ротации.

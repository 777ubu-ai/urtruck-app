Статус: **разрешение получено, интеграция не активна (pending-integration).**

## 1. Основание
- Письмо АО «Информационно-учётный центр» (gosreestr.kz) **№ А-СТЛ/26-956 от 04.05.2026**
  в ответ на обращение ТОО «ALLATAU AED» (ИИН 081240012562), № ЗТ-2026-01704182 от 22.04.2026.
- Интеграционные сервисы СЭО опубликованы на платформе **Smart Bridge**:
  - **Ключ сервиса:** `CargoRuqsatAppsServiceSync`
  - **Паспорт сервиса:** `ORGAM-S-9317` — https://sb.egov.kz/services/passport/ORGAM-S-9317
- Доступ открыт для гос/негос ИС и мобильных приложений.

## 2. Условия подключения (обязательные, орг-/юр-уровень ALLATAU AED)
Из письма — без этого боевые креды Smart Bridge не выдаются:
1. Соблюдение ЗРК «О персональных данных и их защите» и «Об информатизации».
2. ПП РК от 20.12.2016 № 832 (единые требования в области ИКТ и ИБ).
3. Приказ МИК РК от 29.03.2018 № 123 (Правила интеграции объектов «электронного правительства»).
4. **Положительные протоколы испытаний на соответствие требованиям ИБ.**
5. **Действующий договор с оперативным центром ИБ (ОЦИБ).**

> Эти шаги выполняет организация (ALLATAU AED). Код их не закрывает —
> результатом будут учётные данные подключения к Smart Bridge
> (consumer key + TLS-сертификаты), выданные на нашу ИС.

## 3. Что нужно разработчику, чтобы написать боевой клиент
Сейчас паспорт `ORGAM-S-9317` за авторизацией Smart Bridge — технический контракт
из кода недоступен, **схему вызовов вслепую не выдумываем**. Для реализации нужно:
- [ ] Экспорт паспорта сервиса / **WSDL или OpenAPI** (методы, поля запроса/ответа).
- [ ] Протокол (SOAP-через-СШЭП или REST), endpoint(ы) prod/test.
- [ ] Модель авторизации: consumer key, mTLS-сертификаты (пути/пароли).
- [ ] Перечень операций и какие из них нам нужны (см. §4).
- [ ] Подтверждение, что креды уже выданы (или статус процесса по §2).

## 4. Какие данные включаем при интеграции (и где они появятся в UI)
Архитектура: **бэкенд UrTruck = подключаемая ИС (server-to-server, mTLS)**.
Мобильное приложение НЕ ходит в Smart Bridge напрямую (§7 ТЗ: не оборачивать CGR
в WebView, не проксировать ЭЦП/SMS). Фронт не меняется — он уже читает
`GET /api/v1/borders/grouped`; меняется только источник внутри бэкенда.

| Поле в `/borders/grouped` | Сейчас | После интеграции |
|---|---|---|
| `queue_count` | `null` | реальное число машин в очереди КПП |
| `wait_time` | `null` | ориентир времени ожидания |
| `last_updated` | `null` | время среза данных СЭО |
| `queue_status` | `"pending-integration"` | `"live"` (или статус КПП) |
| виджет «позиция по госномеру» | pending-integration | позиция авто в очереди по госномеру из СРТС |

**НЕ реализуем без отдельного решения:** бронирование с ЭЦП и любые операции,
требующие подписи/SMS-аутентификации гражданина (§7 ТЗ — правовой риск).
Нам для UI нужны read-операции: статус/очередь по КПП и позиция по госномеру.

## 5. План включения (когда есть креды + спецификация)
1. Расширить `cgr/settings.py` боевыми полями Smart Bridge (уже добавлены плейсхолдеры
   `CGR_SB_*`, по умолчанию выключено).
2. Реализовать метод(ы) в `cgr/client.py` строго по WSDL/OpenAPI паспорта.
3. В `services/border_service.py` — если `CGR_SB_ENABLED=true` и данные свежие,
   подставлять реальные `queue_count/wait_time/last_updated`; иначе сохранять
   текущий honest-fallback `pending-integration`.
4. Виджет по госномеру — отдельный read-метод (позиция по гос. номеру).
5. Пруфы (ТЗ §8): реальный ответ Smart Bridge (test-контур), запись среза в
   `cgr_scoreboard`, curl `/borders/grouped` с живыми числами.

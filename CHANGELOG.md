# Changelog

Все заметные изменения веб-версии UrTruck (urtruck.kz) фиксируются здесь.
Формат — [Keep a Changelog](https://keepachangelog.com/), версии — [SemVer](https://semver.org/).

Нативные билды (App Store / Google Play) версионируются отдельно в `app.json`
(`version` / `buildNumber` / `versionCode`) и в этот файл не попадают.

## [2.1.2] - 2026-08-19
### Ops note
- Retrigger деплоя после мержа PR #234 (реальный маршрут по дорогам
  KZ/RU через Yandex Router API + надёжные PDF-вложения). Прошлый
  прогон `UrTruck Secure Production Deploy` упал на новом шаге
  «Preflight Yandex Router before touching production» — `401
  Unauthorized` от `api.routing.yandex.net`, потому что `YANDEX_ROUTER_API_KEY`
  в тот момент был пуст, и CI подставлял вместо него `YANDEX_MAPS_JS_API_KEY`
  (другой продукт Yandex, не подходит для Router API). Владелец подтвердил,
  что `YANDEX_ROUTER_API_KEY` уже добавлен в GitHub Secrets — этот коммит
  просто перезапускает пайплайн (у используемой интеграции нет прав
  `workflow_dispatch`/`rerun_failed_jobs` напрямую).

## [2.1.1] - 2026-08-19
### Fixed
- **Иконка избранного — откат обратно на флажок (bookmark).** Запись
  2.1.0 ниже ошибочно поменяла карточки ленты с флажка на сердце, решив
  «выровнять» несоответствие в сторону `FavoritesScreen`. Владелец явно
  подтвердил обратное: канон — флажок везде. Вернули флажок в
  `FeedCard.js`/`CargoFeedScreen.js` и **также перевели `FavoritesScreen`
  на флажок** (он был единственным местом с сердцем изначально — вот и
  была визуальная нестыковка со скриншотов, а не наоборот).

Отдельно (не в этом релизе, см. PR #234): карта не строила маршрут по
дорогам («Алматы → Москва» рисовалось прямой линией через Узбекистан/
Туркменистан) — root cause и фикс уже в работе в параллельном,
более раннем и широком PR (заодно чинит PDF-вложения в чате сделки),
намеренно не дублирую здесь во избежание конфликта решений.

## [2.1.0] - 2026-08-18
### Fixed
- **Избранное**: `FavoritesScreen` запрашивал только `item_type='driver'` —
  грузы, сохранённые водителем через ❤️ на карточке (`CargoFeedScreen`),
  реально писались в БД, но никогда не показывались в «Избранном» (первая
  причина бага с владельческих прод-скриншотов). Теперь один запрос
  `favList('')` покрывает оба типа; список умеет открыть и удалить
  driver- и cargo-запись.
- Иконка сохранения на карточках ленты (`FeedCard.js`, `CargoFeedScreen.js`)
  временно поменяна с флажка (bookmark) на сердце. **Ошибочно — см. 2.1.1
  выше, откачено обратно на флажок по прямому подтверждению владельца.**
- Отзывы под карточкой водителя (`priceCaption`) были помечены как «kept
  for API compatibility; intentionally not rendered» — мёртвый проп,
  реальные данные с бэкенда просто не показывались. Рендер восстановлен.
- Добавлен разовый scoped admin-эндпоинт для очистки 3 известных
  тест-аккаунтов из «Избранного» (см. `backend/api/admin.py`,
  `cleanup-known-test-favorites-2026-08-19`) — те же аккаунты, что уже
  подтверждены тестовыми в 2.0.7/2.0.10.

См. PR #231 для полной картины (root cause по каждому багу, тесты).

### Ops note
- 2026-08-18: два независимых сбоя `UrTruck Secure Production Deploy`
  подряд не связаны с этим фиксом — (1) `Bootstrap secure server-only
  environment` падал на `OPENROUTESERVICE_API_KEY missing` (секрет для
  фичи глобального роутинга из PR #230 не задан/не долетает до сервера),
  (2) следующий прогон завис на тривиальном шаге `apt-get install
  sshpass` на 35 минут и был отменён по таймауту раннера. Этот коммит —
  сознательный retrigger пайплайна на чистом раннере.

## [Rollback to 2.0.0] - 2026-07-30
### Reverted
- Owner-решение: полный откат прода к базовой точке `v2.0.0` (до всех
  правок этой сессии — 2.0.1..2.0.10). Причина: при проверке эндпоинта
  чистки дубли-комнат чата (`cleanup-fake-chat-rooms`) масштаб оказался
  сильно больше ожидаемого (48 комнат вместо ~6 на скриншоте), часть
  переписок выглядела как реальные личные/деловые сообщения, а не тест
  — решили не рисковать и откатиться, разбираться заново отдельно.
- Откачены файлы (`git checkout v2.0.0 --`): `FeedCard.js`,
  `FeedScreen.js`, `BottomNav.js`, `TripDetail.js`, `backend/api/admin.py`,
  `backend/api/chat.py`, `package.json`. Ничего не удалено из БД — на
  проде эндпоинты чистки вызывались только с `dry_run=true`, реального
  удаления комнат/рейсов сверх уже подтверждённых 11 рейсов (см. записи
  2.0.6/2.0.7 выше) не производилось.
- `v2.0.0` как тег остаётся точкой отсчёта; последующая работа
  продолжится отдельными новыми версиями поверх этого отката.

## [2.0.10] - 2026-07-30
### Added
- Backend: `POST /admin/cleanup-fake-chat-rooms-2026-07-30` — разовый
  admin-эндпоинт для чистки дубли-комнат чата у известных тестовых
  аккаунтов (Ali Li / Cvbbb Zcvvvb / Жиенгалиев Миржан), накопленных до
  фикса v2.0.9. Критерий: оставляет только комнаты, привязанные к
  реальной сделке (`deals.chat_room_id`), остальное для этих 3
  аккаунтов удаляет (включая комнаты с сообщениями, но без сделки —
  owner подтвердил явно). Скоуп жёстко ограничен списком известных
  тестовых driver_id — не общая чистка (не трогает pre-deal переписки
  будущих реальных пользователей).

## [2.0.9] - 2026-07-30
### Changed
- **Один чат на пару пользователей вместо пары+груз/рейс.** `_deal_key`
  (backend `api/chat.py`) раньше включал `cargo_id`/`trip_id` — тот же
  собеседник, но другой груз/рейс, давал отдельную комнату. В «Сделках»
  → «Чаты» это выглядело как дубли (часть вообще без сообщений). Теперь
  ключ — только отсортированная пара участников; переписка про разные
  грузы/рейсы с одним и тем же человеком идёт в одну комнату.
  Затрагивает только НОВЫЕ комнаты — уже существующие (созданные до
  деплоя) не трогает и не сливает: `_migrate_canonical_rooms` одноразовая
  и не пересчитывает старые `deal_key` задним числом. Ретроактивное
  слияние существующих дублей — отдельная задача (риск для FK в
  deals/notifications), сознательно не в этом релизе.
  Проверено локально: два сообщения о двух разных рейсах одному
  водителю попадают в один `room_id`.

## [2.0.8] - 2026-07-30
### Fixed
- **TripDetail «Написать водителю» открывал чат без адресата.** `driverId`
  (state) заполнялся только внутри `applyDeal()` — то есть только когда
  сделка уже существует. Кнопка же именно для случая "сделки ещё нет",
  так что `driverId` был всегда `null` в момент клика: чат открывался
  без partner id, показывал generic "Пользователь UrTruck" вместо
  реального имени водителя, а при попытке написать backend отвечал 400
  (`room_id или to_user_id обязателен`) — сообщение физически не уходило.
  Теперь используется `trip.driverId`/`trip.driverName` (доступны сразу
  из `normalizeTrip`, без деалов). Проверено локально: имя резолвится
  сразу, сообщение реально доставляется.

## [2.0.7] - 2026-07-30
### Added
- Backend: `POST /admin/cleanup-fake-trips-2026-07-30-batch2` — второй
  разовый admin-эндпоинт. Owner подтвердил, что оставшиеся 3 "именных"
  аккаунта (Cvbbb Zcvvvb/+7747..., Ali Li, Жиенгалиев Миржан) — тоже
  внутренние тестовые/dev-аккаунты, несмотря на пройденную OTP-

  реальными ставками намеренно не включены — по ним отдельно
  проверяется bidder_id перед удалением.

## [2.0.6] - 2026-07-30
### Added
- Backend: одноразовый admin-эндпоинт `POST /admin/cleanup-fake-trips-2026-07-30`
  (Basic Auth) — удаляет 9 конкретных сид/дубликат-рейсов с прод-фида
  (driver_name=null/мусорное имя, verified=false, маршруты дублируют
  реальные записи). `dry_run=true` по умолчанию — только показывает
  список, `dry_run=false` удаляет. Пропускает записи, если на них есть
  ставки/сделки (та же защита, что у `cleanup-stale-listings`).
  Список id захардкожен вручную по owner-запросу, не общий алгоритм.

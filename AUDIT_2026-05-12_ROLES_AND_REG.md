## 0. TL;DR

Текущий билд — **роль-агностичная одностраничная лента + один общий
bottom nav для всех**. Регистрация идёт **role-first → phone → SMS →
profile**, а должно быть **phone → SMS → role → profile** (inDriver-стиль).

Это **не косметика** — это архитектурный долг, который тянется ещё с MVP
v0/v1.0 и который Phase 1/2A не лечит. Phase 2A только **усилил**
одинаковость (унифицированный оранжевый акцент вне зависимости от роли,
см. ниже).

Чинить надо **отдельным релизом** (релиз-кандидат `rc2`), не дописывая
поверх RC1. Build (9) на TestFlight остаётся как есть.

## 2. Проблема №1: смешанная лента «грузы + рейсы»

### Где это в коде

**`src/screens/FeedScreen.js:183-191`** — корень проблемы:

```js
// guestRole: гость может переключаться между "я водитель" / "я клиент"
// прямо в шапке. Авторизованный пользователь этого не видит, у него
// role зашита в session.
const sessionRole = session?.user?.role || null;
const isGuest = !sessionRole;
const [guestRole, setGuestRole] = useState(route.params?.role || 'driver');
const role = isGuest ? guestRole : (sessionRole || route.params?.role || 'client');
const isDriver = role === 'driver';
```

**`src/screens/FeedScreen.js:597-633`** — рендер этого переключателя в
шапке, только для `isGuest`:

```jsx
{isGuest && (
  <View style={s.guestTabs}>
    <TouchableOpacity onPress={() => setGuestRole('driver')} ...>
      <Text>{t('guest_tab_cargos')}</Text>   {/* «Грузы» */}
    </TouchableOpacity>
    <TouchableOpacity onPress={() => setGuestRole('client')} ...>
      <Text>{t('guest_tab_trips')}</Text>     {/* «Рейсы» */}
    </TouchableOpacity>
  </View>
)}
```

### Что это значит на практике

- **Гость (без сессии) видит переключатель.** Это и есть «грузы и рейсы
  на одной странице» из жалобы.
- **Авторизованный водитель видит только грузы.** Авторизованный
  грузовладелец видит только рейсы. Здесь всё, по идее, корректно.
- НО: пользователь жаловался именно на гостевой режим, потому что:
  1. Это первый экран, который видит человек, нажавший «Смотреть ленту»
     с RoleScreen → `navigation.navigate('Main', { role: 'driver',
     guest: true })` (см. `RoleScreen.js:81`).
  2. Подзаголовок и CTA «Опубликовать маршрут» / «Опубликовать груз»
     меняются вместе с переключателем — это создаёт впечатление, что
     приложение «не понимает, кто я».

### Почему это болит для B2B

Логистический B2B-маркетплейс работает по правилу «**одна роль — один
продукт**». Грузовладелец **никогда** не должен видеть «рейсы»,
водитель — «грузы из чужого профиля». Текущая мешанина:

- сбивает онбординг (юзер не понимает, что он покупает);
- бьёт по доверию: международные перевозчики и логисты не пользуются
  приложениями «без позиции»;
- ломает сегментацию аналитики (один и тот же fingerprint смотрит то
  одни данные, то другие — невозможно нормально считать конверсию по
  ролям).

### Дополнительно: Phase 2A унифицировал акцент

PR #28 (HEAD `96cdaa0`) специально **убрал** различие цвета по ролям:

> `src/components/ui/v1/BottomNav.js:69-73` — комментарий из PR:
> > Phase 2A: единый orange-accent ради взрослой B2B-палитры. role
> > влияет только на то, какие иконки/тексты табов мы показываем, но
> > цвет акцента уже не зависит от роли.

Это решение **правильное визуально** (один accent = один продукт), но
оно **усугубляет** жалобу: теперь по цветовой кодировке нельзя понять,
в каком ты режиме. Если архитектурно «грузы и рейсы вместе», то на
скрине это совсем выглядит как «приложение для всех сразу».

## 3. Проблема №2: один навигатор на две роли

### Где это в коде

**`src/navigation/AppNavigator.js:64-89`** — `MainTabs` один для всех:

```jsx
function MainTabs({ route }) {
  const { session } = useAuth();
  const role = session?.user?.role || route?.params?.role || 'client';
  // ...
  return (
    <Tab.Navigator tabBar={(props) => <BottomNav {...props} />}>
      <Tab.Screen name="Feed"    component={FeedScreen}      initialParams={{ role }} />
      <Tab.Screen name="MyWork"  component={MyTripsScreen}   initialParams={{ role }} />
      <Tab.Screen name="Publish" component={PublishStub}     initialParams={{ role }} />
      <Tab.Screen name="Chats"   component={ChatsListScreen} initialParams={{ role }} />
      <Tab.Screen name="Profile" component={ProfileScreen}   initialParams={{ role }} />
    </Tab.Navigator>
  );
}
```

`role` пробрасывается **параметром** в каждый экран, и **каждый экран
сам решает, как рендериться**:

- `FeedScreen` → грузы или транспорт;
- `MyTripsScreen` → «мои рейсы» или «мои грузы»;
- `Publish` → `CreateTrip` или `CreateCargo` (см. `BottomNav.js:114-116`);
- `ChatsListScreen` → одинаковый;
- `ProfileScreen` → одинаковый.

### Что это значит на практике

- **Нет физического разделения** между «приложение для водителя» и
  «приложение для грузовладельца». Это одно приложение, которое внутри
  каждого экрана делает `if (isDriver) {...} else {...}`.
- **Невозможно отдельно эволюционировать UX по ролям.** Например,
  у грузовладельца со временем понадобятся таб «Аналитика расходов»
  или «Контракты», а у водителя — «Маршруты» или «Очереди на
  границе». Сейчас любой новый таб надо добавлять одновременно
  обеим ролям.
- **QA-матрица удваивается на каждый экран.** Каждый pull request,
  трогающий FeedScreen или MyTripsScreen, теперь должен быть проверен
  в двух режимах (driver/client) + guest-overlay. Это бутылочное
  горлышко при росте команды.

### Как должно быть (вариант, который соответствует жалобе)

Два независимых `Tab.Navigator`-а, выбираемых на уровне
`AppNavigator`:

```
если session.user.role === 'driver':
   DriverTabs:  Грузы | Мои рейсы | + | Чаты | Профиль
если session.user.role === 'client':
   ClientTabs:  Транспорт | Мои грузы | + | Чаты | Профиль
если гость (нет session):
   GuestTabs:   Лента (выбор «я водитель / я клиент» — но один раз, не toggle в шапке)
                | Войти | (опционально: Поддержка)
```

Это снимает:
- toggle «Грузы/Рейсы» из шапки `FeedScreen`;
- `isGuest`-ветку в `FeedScreen`;
- условные `if (isDriver)` внутри tab-bar (BottomNav становится тонким);
- удвоение QA-матрицы.

## 4. Проблема №3: регистрация role-first вместо phone-first

### Текущий flow (build 9)

```
1. Splash
2. Onboarding (3 слайда)
3. RoleScreen
     ├─ «Зарегистрироваться как водитель» → enterAs('driver') → Reg(role=driver)
     ├─ «Зарегистрироваться как грузовладелец» → enterAs('client') → Reg(role=client)
     ├─ «Уже есть аккаунт? Войти» → Login
     └─ «Смотреть ленту · Без регистрации» → Main (guest)
4. PremiumRegisterScreen (phone+consent с role-badge сверху)
5. PremiumOtpScreen (SMS-код)
6. PremiumProfileScreen (имя, город) — role-badge сверху
7. Main (с этой ролью)
```

Подтверждения в коде:
- `src/screens/RoleScreen.js:114` → `navigation.navigate('Reg', { role })`
- `src/screens/registration/PremiumRegisterScreen.js:115` → `navigation.navigate('RegOtp', { ... role, phone, ... })`
- `src/screens/registration/PremiumOtpScreen.js` — переход на `RegProfile`
- `PremiumRegisterScreen.js:169` показывает «🚛 Водитель» / «📦 Грузовладелец» как chip в шапке

### inDriver-стиль flow (как написал владелец)

```
1. Splash + краткая фирменная заставка
2. PhoneScreen (только телефон, без выбора роли) ← главный отличий
3. OtpScreen (SMS-код)
4. RoleScreen (теперь после auth — «вы вошли как +7..., выберите роль»)
     ├─ Водитель → DriverProfile (имя + транспорт + город)
     └─ Грузовладелец → ClientProfile (имя + компания + город)
5. Main (по роли)
```

Что это даёт:
- **Меньше психологического трения.** Юзер сначала «подтверждает себя»
  телефоном — это короткое и понятное действие, ниже барьер входа.
  inDriver / Yango / Uber так и работают.
- **Роль = реальная.** Сегодня юзер может нажать «грузовладелец» из
  любопытства и не довести регистрацию. Если телефон уже подтверждён —
  выбор роли осознаннее (понятно, что это не «посмотреть», а «зайти как»).
- **Возможность одной учётке иметь две роли.** В inDriver один номер
  может быть и пассажиром, и водителем. У нас сейчас один phone =
  одна role жёстко (см. PremiumOtp `prem_reg_existing_account` ветку).
- **Лучше для аналитики.** Логи telephony, retention по shape phone
  cohort, а не shape role cohort.

### Стоимость переделки

- 3 экрана меняют порядок навигации (`RoleScreen` теперь после OTP).
- Backend: эндпоинты регистрации/OTP сейчас принимают `role` в payload
  на этапе **отправки SMS** (`PremiumRegisterScreen.js:115` шлёт
  `{ role, phone }` в `/api/v1/register/...`). Надо разрешить SMS без
  role и принимать role на этапе создания профиля.
- Тесты: e2e flow меняется (Maestro/Playwright скрипты, если есть).
- i18n: ключи `prem_reg_phone_title_driver`/`_client` сворачиваются в
  один общий `prem_reg_phone_title`.

Это **не маленькое изменение**, но **тоже не двухнедельное** — где-то
2-3 дня одного разработчика + день QA, если backend не сопротивляется.

## 6. Прочие архитектурные находки попутно

В ходе аудита всплыло, что стоит зафиксировать (не блокер, но в долг):

1. **`MainTabs` тянет `role` через `route.params?.role`** как fallback,
   но `route` для bottom-tab-screen — это route таб-навигатора, а не
   родительского Stack. Когда юзер заходит через `navigation.reset →
   Main`, `route.params.role` приходит. Когда заходит реактивно после
   `setRole()` — НЕ приходит, и срабатывает дефолт `'client'`. Это
   баг прямо сейчас для свежезарегистрированного водителя.
   `src/navigation/AppNavigator.js:66`.

2. **Гостю в `RoleScreen.js:81` навязывается `role: 'driver'`** для
   «смотреть ленту». Это значит, что гость видит грузы по умолчанию.
   Если переключателя в шапке не было бы, гость никогда не увидел
   бы транспорт. То есть `guestRole`-toggle компенсирует кривое
   решение «дефолт = driver».

3. **`MyTripsScreen` ребрендится через `route.params.role`** —
   проверить, что заголовок не мигает на «Мои грузы» у водителя при
   реактивной смене роли.

4. **`ChatsListScreen` и `ProfileScreen`** — одинаковые для обеих
   ролей. Если разделим navigation — надо заложить, что в чате
   водителя список собеседников = грузовладельцы (с их грузом-pinned),
   у грузовладельца = водители (с их транспортом-pinned).

5. **`Publish` cell** в bottom nav — `BottomNav.js:113-117` интерсептит
   tab press и навигирует на CreateTrip / CreateCargo. После разделения
   nav-стеков это упрощается — у driver всегда `CreateTrip`, у client
   всегда `CreateCargo`, без условия.

6. **`MainTabs` нет `MyWork` для гостя** — но он и не должен быть
   виден гостю. Сейчас гость может перейти в MyWork таб и увидеть
   пустоту (или ошибку API без auth-токена). Надо проверить.

## 7. Предлагаемый план (без согласования — на обсуждение)

### Эпик RC2-A: «Разделение ролей»

Цель: водитель и грузовладелец видят **разные приложения** с момента
авторизации.

Стадии:

| Стадия | Объём | Риск |
|---|---|---|
| A1 | Завести `DriverTabs` и `ClientTabs` (два `Tab.Navigator`-а) | низкий |
| A2 | Переключение в `AppNavigator` по `session.user.role` | низкий |
| A3 | Удалить `guestRole`-toggle из `FeedScreen` (см. эпик B) | низкий |
| A4 | Локализация: убрать `guest_tab_cargos` / `guest_tab_trips` | минимальный |

### Эпик RC2-B: «Гостевой режим без двух лент»

Цель: гость попадает **либо** на feed грузов, **либо** на feed
транспорта — выбор делает один раз, без переключателя в шапке.

Варианты:
- B-opt-1: гость = всегда «смотрю грузы как водитель». Чтобы посмотреть
  транспорт — нужно зарегистрироваться как client. Это спартанский, но
  честный вариант.
- B-opt-2: гость видит **третий тип ленты — публичную**: микс свежих
  грузов и свежих рейсов без CTA «отозваться» (CTA приводит к
  регистрации). Это похоже на classifieds-стиль (Avito).
- B-opt-3: гость отключён вообще. Без auth — только Splash/Onboarding/
  RoleScreen, никакой ленты. Самый жёсткий, но самый предсказуемый.

→ **Вопрос владельцу:** какой вариант B оставляем?

### Эпик RC2-C: «inDriver-style регистрация»

Цель: phone → SMS → role → profile.

Стадии:

| Стадия | Объём | Риск |
|---|---|---|
| C1 | `PremiumLoginScreen` становится первым экраном (без выбора роли) | средний |
| C2 | `PremiumOtpScreen` принимает payload без `role` | средний (backend) |
| C3 | Новый `PremiumRoleScreen` после OTP (или переиспользуем `RoleScreen`, но в режиме «уже авторизован») | низкий |
| C4 | `PremiumProfileScreen` получает role из state после C3 | низкий |
| C5 | Backend `/api/v1/register/send-otp` — role становится optional | средний |
| C6 | `RoleScreen` (текущий welcome) превращается в **онбординг**: лозунг + одна кнопка «Начать» → `PremiumLoginScreen` | низкий |

### Эпик RC2-D: «Технический долг попутно»

См. раздел 6. Маленькие пункты на гигиену, делаются вместе с A/B/C.

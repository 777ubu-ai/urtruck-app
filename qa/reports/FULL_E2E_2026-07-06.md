## Почему Playwright, а не Maestro

Maestro Web в этом окружении **не запускается**: `maestro test -p web` (и
`--platform=web`, и appId-URL) всегда рапортует `0 devices connected`. Всё нужное
на месте (Maestro 2.6.0, `maestro-web.jar`, `selenium-chromium-driver`, Chrome,
`start-device --platform web` реально поднимает `chromedriver`), но web-«устройство»
не регистрируется в раннере. Единственная JDK — **Java 26** (Temurin), web-поддержка
Maestro 2.6.0 — beta и, по всем признакам, несовместима с Java 26 / macOS 26.

Решение согласовано с владельцем: гнать ту же ПОЛНУЮ e2e на том же собранном
веб-UI через Playwright (тот же `dist/` + прокси, реальные экраны, скриншоты).
Цель и артефакт сохранены — сменился только драйвер.

**Итог прогона:** `11 passed` (~26 c).

## БАГИ

### BUG-1 (P1) — ✅ ИСПРАВЛЕН — email-владелец не мог принять/отклонить ставку в UI

**Фикс применён** (по согласованию — вариант «ослабить гейт id-синка»):
`src/utils/AuthContext.js` — `refreshLevel` теперь синкает реальный backend-`id`
в сессию всегда, когда он известен (даже при `role==='guest'`); клиентская роль
(выбранная на RoleV2) при этом не затирается на `guest`. Проверено e2e: владелец-email
видит owner-view и принимает ставку через UI (`D2` PASS, скрин `D2_01`).
Ниже — исходная диагностика.

---

**Где:** `src/utils/AuthContext.js:36` (гейт синка id) + `src/screens/CargoDetail.js:155`
(owner-check) + `backend/api/registration.py` (email_verify).
**Симптом:** зашедший по email грузовладелец на экране своего груза (CargoDetail)
видит **bidder-view**: снизу CTA «Предложить цену», у ставки нет кнопок
`bid-accept`/`bid-reject`/`bid-counter`. Принять ставку через UI невозможно.
**Корень:**
1. `email_verify` создаёт/возвращает пользователя с ролью **`guest`** и НИКОГДА её не
   меняет. Роль, выбранная на RoleV2, ставится только в клиентском состоянии
   (`AuthContext.setRole`) и на бэк не уходит (`regAPI.updateProfile` роль не шлёт;
   экран ProfileV2, который мог бы дослать, на вебе пропускается — см. Obs-1).
   Подтверждение: `GET /register/me` и `GET /users/me` для email-юзера → `role: "guest"`.
2. `refreshLevel` синкает реальный backend-id в сессию **только если**
   `me.role && me.role !== 'guest'` (AuthContext.js:36). Роль `guest` → синк
   пропускается → `session.user.id` остаётся синтетическим `u_<timestamp>`.
3. CargoDetail считает владельца как `fullCargo.owner_id === session.user.id`
   (CargoDetail.js:155). `owner_id` = реальный driver_id, `session.user.id` = синтетика
   → **не совпадают** → isMine=false → bidder-view.

**Репро:**
1. Вход по email как клиент → создать груз.
2. Любой водитель ставит ставку на этот груз.
3. Тем же email снова войти, открыть груз (Мои грузы → предложения).
4. Ожидание: кнопки Принять/Отклонить. Факт: bidder-view, кнопок нет.

**Почему у телефона нет:** `wa_verify` (BETA и реальный) присваивает роль на бэке
(driver), поэтому `refreshLevel` синкает id и owner-check срабатывает. Баг
специфичен для **email-канала**.

**Влияние:** email-владелец не может вести сделку из UI (accept/reject/counter,
deal-room). Затрагивает и любые другие `isMine`-gated элементы для email-юзеров.

**Фикс (НЕ применял — graphify-gated: backend-регистрация + AuthContext; жду решения).**
Варианты:
- (реком.) `backend/api/registration.py::email_verify` — принимать `role` (он уже есть
  в `EmailSendRequest`, добавить в verify или брать из сохранённого) и проставлять роль
  драйверу вместо `guest`; ИЛИ
- ослабить гейт в `AuthContext.js:36`, синкая `me.id` даже при `role==='guest'`
  (id не зависит от роли) — точечно и безопасно; ИЛИ
- гарантировать прохождение ProfileV2 (updateProfile) — но это меняет навигацию (Obs-1).

## НАБЛЮДЕНИЯ

### Obs-1 — ProfileV2 (имя/город) пропускается на вебе
После выбора роли на RoleV2 `setRole` делает `hasRole=true`, и `AppNavigator`
реактивно переключается на аутентифицированный стек (Main) — а `ProfileV2` живёт в
pre-auth стеке, поэтому `navigate('ProfileV2')` не успевает и юзер попадает сразу в
Main. Имя/город новых пользователей не собираются (пусты). Наблюдалось для обеих
ролей; не только email. Не баг email-канала, но усугубляет BUG-1 (роль/профиль на
бэк не дослались).

### Obs-2 — MOCK vs BETA
При `URTRUCK_ENV=development` активен `BETA_MODE` → `email/send` идёт beta-веткой
(`mock:false`, код не в ответе), verify принимает `0000`. «Честный» код в ответе —
только при `BETA_MODE=false` (проверено на :8002). Оба режима — норма для MOCK.

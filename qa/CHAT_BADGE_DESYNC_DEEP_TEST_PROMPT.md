# ГЛУБОКИЙ ТЕСТ-ПРОМПТ: рассинхрон уведомлений и бейджей чата

> Цель: до запуска железно понять и закрыть рассинхрон «иконка приложения ↔ красная
> точка внутри приложения ↔ колокольчик» в чате. Тормоза, зависания, «есть на иконке —
> нет внутри» / «есть внутри — нет на иконке», «прочитал внутри — на иконке осталось».
>
> Этот документ — **промпт для исполнителя** (человек на двух телефонах + Maestro + API).
> Он не из головы: каждая гипотеза привязана к конкретному коду. Сначала — карта системы и
> гипотезы, потом — матрица вариантов, потом — как именно проверять (manual / Maestro / API),
> потом — шаблон сбора данных и критерии PASS/FAIL.

---

## 0. Симптомы (со слов владельца, дословно)

1. «Очень тормозит, зависает».
2. «То в одной стороне появится — например, на иконке стоит, а внутри приложения нет».
3. «Или в обоих местах появляется; заходишь в приложение, видишь красным где сообщение,
   потом выходишь — а на иконке по-любому остаётся».

Это **не один баг, а минимум три разных** (задержка, односторонняя доставка, незатухание
иконки). Тестировать их надо раздельно — иначе «починили одно, а кажется что не работает».

## 1. Карта системы — ТРИ независимых счётчика

| # | Счётчик | Где видно | Кто пишет | Источник числа |
|---|---|---|---|---|
| C1 | **Бейдж на иконке приложения** | домашний экран iOS/Android | (a) бэк через APNS/FCM `badge`; (b) клиент `setBadgeCountAsync` | (a) server unread на момент push; (b) `chatUnread` в BottomNav |
| C2 | **Красная точка «Чаты»** | нижний таб-бар, внутри app | `BottomNav` | `chatAPI.unread()` (поллинг 30с) + `subscribeChatRead` + AppState |
| C3 | **Колокольчик** | экран Feed | `FeedScreen` | `getUnreadNotifications()` из `store.js` (локальный стор, НЕ чат) |

**Ключевой факт: C1, C2, C3 считаются по-разному и не сверяются.** Любое расхождение между
ними воспринимается как «баг уведомлений».

### Точные места в коде
- **C1 — бэк:** `backend/services/push_sender.py`
  - `_compute_recipient_badge(user_id)` (≈ строка 220): `COUNT(*)` непрочитанных chat-сообщений получателя.
  - `send(...)` (≈ 242): `badge` считается **только** если `kind=='chat'` или `data.type=='chat_message'`. Для `bid`/`system` badge=None (иконку не трогают). APNS сам рисует кружок по полю `badge`.
- **C1 — клиент:** `src/components/ui/v1/BottomNav.js`
  - `useEffect([chatUnread])` (≈ 126): `Notifications.setBadgeCountAsync(chatUnread)`. **Срабатывает только если BottomNav смонтирован И значение `chatUnread` изменилось.** Ошибки глотаются `.catch(()=>{})`. На web — noop.
- **C2:** `BottomNav.js` `useEffect([hasToken])` (≈ 86): `fetchUnread()` на mount, каждые `UNREAD_POLL_MS=30000`, на `AppState='active'`, и на `subscribeChatRead`.
  - `src/utils/chatAPI.js` `unread()` (≈ 47): **short-circuit в `{unread:0}`** если нет токена или `ur_verification_level < 1` (гость); и **`{unread:0}` на любой `!r.ok`** (глотает ошибку/таймаут).
  - `src/utils/unreadEvents.js`: `notifyChatRead()` дёргается из `ChatScreen` на mount/unmount.
- **Пометка прочитанным:** `backend/api/chat.py` `get_messages` (≈ 513): `UPDATE chat_messages SET is_read=1 WHERE room_id=? AND sender_id!=? AND is_read=0` — **помечает прочитанной только ОТКРЫТУЮ комнату**.
- **/unread (server):** `backend/api/chat.py` `unread_count` (≈ 562) — COUNT по всем комнатам пользователя, `sender_id != uid`, `is_read=0`.
- **Foreground push-handler:** `src/utils/push.js` `setNotificationHandler` (≈ 132): для активной открытой комнаты `shouldSetBadge:false`, иначе `shouldSetBadge:true` (Expo инкрементит иконку в foreground).

## 2. Гипотезы корневых причин (H1–H8) — что именно проверяем

Каждый сценарий ниже помечен гипотезой, которую он подтверждает/опровергает.

- **H1 «Иконка не затухает после прочтения».** C1 чистится только когда `chatUnread` в
  BottomNav **меняется** на 0. Если на момент прочтения `chatUnread` уже был 0 (push пришёл
  при убитом app → состояние стартовало с 0; или прочитали через тап по push, минуя
  изменение стейта) → эффект `setBadgeCountAsync(0)` **не вызывается** → APNS-кружок висит.
- **H2 «Есть на иконке, нет внутри».** C1 поставил бэк (APNS badge), а C2 (`chatAPI.unread()`)
  вернул 0 из-за: гостевого short-circuit (`level<1`), `!r.ok` (таймаут/5xx/401 глотается),
  либо поллинг ещё не наступил (до 30с лага).
- **H3 «Есть внутри, нет на иконке».** Бэк не послал badge (kind не chat, или push не дошёл /
  permissions denied / Expo Go), но C2 поднялся по поллингу. Либо `setBadgeCountAsync` молча
  упал (`.catch`), либо web/Expo Go не поддерживает иконку.
- **H4 «Тормозит/лаг до 30с».** C2 обновляется только поллингом 30с + AppState active. Нет
  реального realtime → входящее видно с задержкой. (Плюс ранее: `authedFetch` без таймаута мог
  морозить — уже исправлено в `85cb3c8`, проверить регресс.)
- **H5 «Multi-room: прочитал одну — счётчик не обнулился».** `get_messages` помечает прочитанной
  только открытую комнату. При 2+ комнатах с непрочитанным C1/C2 = сумма; после чтения одной
  должно остаться N−(прочитанные в этой комнате). Проверить, что число корректное, а не «0 или всё».
- **H6 «Своё сообщение увеличивает счётчик отправителю».** `sender_id != uid` должно исключать.
  Регресс недавнего фикса «чат-эхо» (`85cb3c8`) — проверить, что отправитель НЕ получает +1.
- **H7 «Гонка badge: бэк vs клиент».** Бэк ставит APNS badge = server unread; клиент через
  `setBadgeCountAsync` перетирает на `chatUnread`. Порядок недетерминирован (push прилетел до/после
  поллинга) → мигание/неверное число.
- **H8 «Колокольчик (C3) путают с чатом».** `bid`/`deal`-пуши идут в колокольчик (store), НЕ в
  чат, и НЕ ставят иконку (badge=None). Если воспринимать колокольчик как «сообщение» —
  кажется рассинхроном. Проверить, что bid-нотификация не трогает C1/C2.

## 3. Оси вариативности (комбинируем для покрытия)

- **Состояние app:** foreground открыт на чате той же комнаты · foreground на другом экране ·
  background (свёрнут) · killed (убит свайпом).
- **Платформа:** iOS TestFlight (реальный APNS) · Android APK (FCM) · Expo Go (push ограничен) ·
  Web/PWA (иконки нет, C1 noop).
- **Кол-во комнат с непрочитанным:** 0 · 1 · 2+ (multi-room).
- **Где прочитал:** открыл чат внутри app · тап по push-баннеру · тап по иконке (без открытия чата).
- **Сеть:** онлайн · медленная (throttle) · офлайн→онлайн.
- **Кто/кому:** водитель→владелец · владелец→водитель · support-бот.

## 4. Каталог сценариев

> Обозначения: **A** = телефон-владелец, **B** = телефон-водитель. «Observe» = какой счётчик
> смотрим. «Tool» = чем гоняем. Каждый сценарий — отдельный PASS/FAIL.

### Блок S — базовая доставка и затухание

**S1. Foreground, чат закрыт (H4, H2).**
Pre: A и B вошли (разные аккаунты), у обоих 0 непрочитанных. A на экране Feed.
Steps: B отправляет `t-S1` в общую сделку → жди.
Expect: в течение ≤ 30с у A: C2 (точка «Чаты») = 1; C1 (иконка) = 1 (если push дошёл).
Observe: C1, C2. Tool: manual 2 phone + Maestro (только C2).

**S2. Прочтение внутри обнуляет всё (H1, H5).**
Pre: после S1 (у A непрочитано 1).
Steps: A открывает чат-комнату, видит `t-S1`, выходит назад на список, затем сворачивает app и
смотрит на иконку.
Expect: C2 исчезла сразу; C1 на иконке = 0 (исчезла). **Это главный баг — фиксируй точное
поведение.**
Observe: C1, C2. Tool: manual 2 phone.

**S3. Background → входящее ставит иконку (H1, H7).**
Pre: у A 0 непрочитанных, app свёрнут (не killed).
Steps: B отправляет `t-S3`.
Expect: иконка C1 → 1, баннер показан. A разворачивает app (НЕ открывая чат) → C2 = 1.
A открывает чат → выходит → сворачивает → C1 = 0.
Observe: C1, C2. Tool: manual 2 phone.

**S4. Killed → cold start (H1, H2).**
Pre: у A 0 непрочитанных, app убит свайпом.
Steps: B отправляет `t-S4`.
Expect: иконка C1 → 1. A открывает app с иконки (cold start) → C2 = 1 в течение ≤ 30с
(лучше сразу, т.к. fetchUnread на mount). A читает чат → выходит → C1 = 0.
**Подозрение H1: после cold-start `chatUnread` стартует с 0; проверь, реально ли иконка гаснет.**
Observe: C1, C2. Tool: manual 2 phone (iOS TestFlight + Android APK отдельно).

### Блок M — несколько комнат (multi-room)

**S5. Две комнаты, читаем одну (H5).**
Pre: у A непрочитано в ДВУХ разных сделках (по 1 сообщению): `t-S5a` от B1, `t-S5b` от B2
(или одно от B, второе от support).
Expect: C1 = 2, C2 = 2 (точка без числа — но через 9+ должна показывать `9+`; до этого просто точка).
Steps: A открывает только первую комнату, читает, выходит, сворачивает.
Expect: C1 = 1 (НЕ 0, НЕ 2), C2 остаётся. Открывает вторую, читает → C1 = 0, C2 исчезла.
Observe: C1, C2. Tool: manual 2 phone + API-проверка числа /unread.

**S6. Бейдж-число ≥ 10 (H5).**
Pre: накидать 11 непрочитанных в одной комнате (B шлёт 11 сообщений, A не открывает).
Expect: C2 показывает `9+` (`BottomNav`: `chatUnread>9 ? '9+'`); C1 (iOS) показывает реальное `11`.
Observe: C1, C2. Tool: manual + API.

### Блок D — направление и эхо

**S7. Отправитель не получает счётчик (H6).**
Pre: 0 непрочитанных у обоих.
Steps: B отправляет `t-S7` → смотрим на B (отправителя).
Expect: у B C1=0, C2=0 (своё сообщение не считается). У A — растёт.
**Регресс фикса «чат-эхо»: критично.**
Observe: B: C1,C2; A: C1,C2. Tool: manual + API (`unread_count` для sender == 0).

**S8. Двусторонний пинг-понг (H4).**
Steps: B→A `t-S8-1`, A читает, A→B `t-S8-2`, B читает. 5 раундов.
Expect: каждый раунд счётчик появляется у получателя и гаснет после прочтения; у отправителя
не растёт; нет «залипших» значений.
Observe: C1, C2 у обоих. Tool: manual 2 phone.

### Блок X — рассинхрон-ловушки

**S9. Активная комната не должна баннерить (push.js handler).**
Pre: A **открыл и держит открытым** чат-комнату с B.
Steps: B отправляет `t-S9`.
Expect: сообщение появляется в ленте чата сразу (или ≤ poll); баннер НЕ показывается;
иконка НЕ инкрементится (handler `shouldSetBadge:false` для активной комнаты);
после выхода C1/C2 = 0 (т.к. прочитано на лету).
Observe: баннер, C1, C2. Tool: manual 2 phone.

**S10. Тап по push, минуя список (H1).**
Pre: A background, у A 0 непрочитанных.
Steps: B шлёт `t-S10` → A тапает по push-баннеру → открывается комната.
Expect: комната открыта на нужном сообщении; после выхода C1=0, C2=0.
**Подозрение H1: чтение через тап могло не пройти через изменение `chatUnread` → иконка зависла.**
Observe: C1, C2, экран открытия. Tool: manual 2 phone.

**S11. Тап по иконке без открытия чата (H1, H7).**
Pre: у A непрочитано 1, app killed.
Steps: A открывает app с иконки, НО остаётся на Feed (не идёт в чат), сворачивает.
Expect: C1 остаётся 1 (не прочитано) — это корректно. Затем A идёт в чат, читает, выходит,
сворачивает → C1 = 0.
Observe: C1, C2. Tool: manual 2 phone.

**S12. Bid-нотификация не трогает чат (H8).**
Pre: 0 непрочитанных.
Steps: B делает ставку на груз A (это `bid`, не chat).
Expect: у A колокольчик C3 +1; C1 (иконка) НЕ меняется (badge=None для kind!='chat'); C2 (точка
«Чаты») НЕ меняется.
Observe: C1, C2, C3. Tool: manual 2 phone + API.

**S13. Медленная сеть / офлайн (H4, H2).**
Pre: у A включить сетевой throttle (или режим «в самолёте» на 20с).
Steps: B шлёт `t-S13`. У A app открыт.
Expect: при офлайне C2 не падает в ложный 0 и не морозит экран (регресс таймаута `authedFetch`,
фикс `85cb3c8`); при возврате сети C2 = 1 в течение ≤ 30с.
Observe: C2, отзывчивость UI. Tool: manual (Network Link Conditioner / Airplane mode).

**S14. Web/PWA (H3).**
Pre: открыть https://urtruck.kz в браузере под аккаунтом A.
Steps: B шлёт `t-S14`.
Expect: C2 (точка) появляется; C1 (иконки нет в web — это норма, не баг); никаких крашей в консоли.
Observe: C2, console. Tool: manual web + Playwright (см. `tests/e2e`).

## 7. API / pytest — серверные инварианты (фундамент)

Прогнать (и расширить) против локального бэка или прод-реплики БД. Проверяем функции
`unread_count`, `_compute_recipient_badge`, `get_messages` (read-marking):

1. **INV-1:** после `send(a→b)` → `unread_count(b)` +1, `unread_count(a)` без изменений (H6/H7).
2. **INV-2:** `_compute_recipient_badge(b)` == `unread_count(b)` (C1-бэк и C2-источник совпадают).
3. **INV-3:** `get_messages(room, b)` → все непрочитанные в этой комнате становятся `is_read=1`;
   в ДРУГИХ комнатах b — НЕ трогаются (H5).
4. **INV-4:** после чтения одной из двух комнат `unread_count(b)` == число оставшихся (не 0, не всё).
5. **INV-5:** своё сообщение (`sender_id==uid`) никогда не входит в `unread_count` (H6).
6. **INV-6:** bid/system-push не вызывает `_compute_recipient_badge` (badge=None) (H8) — проверка
   логики `send()`.
7. **INV-7 (идемпотентность):** двойной `send` с тем же `client_msg_id` не даёт +2 (дедуп).

Готовый прогон уже частично есть: `backend/tests/test_deal_rooms.py`. Добавить
`backend/tests/test_unread_badge.py` с INV-1…INV-7 (см. раздел 9 — я его уже создал и прогнал).

## 10. Критерии PASS (релизный гейт)

- **G1 (затухание):** после прочтения комнаты иконка C1 и точка C2 = 0 во **всех** состояниях
  (foreground/background/killed, тап-по-push и открытие-из-списка). ← главный.
- **G2 (доставка):** входящее у получателя поднимает C1 и C2; лаг C2 ≤ 30с (цель ≤ 5с — см. P-fix).
- **G3 (направление):** отправитель никогда не получает +1 (C1=C2=0 у себя).
- **G4 (multi-room):** число корректно уменьшается покомнатно, не «0 или всё».
- **G5 (изоляция):** bid/system (C3) не трогают C1/C2; чат не трогает C3.
- **G6 (устойчивость):** офлайн/медленно — нет зависаний экрана, нет ложного вечного спиннера,
  нет ложного 0 после возврата сети.

## 11. Если гейт не зелёный — вероятные фиксы (для следующего шага, НЕ в этом тесте)

- **H1 (иконка не гаснет):** в `BottomNav` синхронизировать иконку не по изменению `chatUnread`,
  а **безусловно** при каждом `fetchUnread` и на `AppState='active'` (вызвать
  `setBadgeCountAsync(server_unread)` всегда, а не только в `useEffect([chatUnread])`). Плюс на
  открытии чата (`ChatScreen` mount) явно дёрнуть пересчёт иконки.
- **H2/H3 (одностороннее):** сделать C2 и C1 из **одного** источника (server unread) и сверять при
  каждом фокусе; не глотать `!r.ok` молча для бейджа (отличать «ошибка» от «0»).
- **H4 (лаг 30с):** уменьшить `UNREAD_POLL_MS` или добавить realtime (SSE/WebSocket/short-poll при
  активном чате); рефетч на фокусе экрана чатов.
- **H7 (гонка):** один писатель иконки. Либо только бэк (APNS badge) + клиент чистит при чтении,
  либо только клиент по server unread. Не оба одновременно без сверки.

> CLAUDE.md сперва анализ связей и подтверждение владельца, потом код.

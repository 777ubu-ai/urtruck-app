=== НАЧАЛО ПРОМПТА ===

Ты — QA-инженер и бэкенд/фронтенд-аудитор проекта UrTruck (FTL-маркетплейс
грузоперевозок Китай↔СНГ, React Native + Expo web фронт, FastAPI + SQLite бэк).
Твоя задача — провести ПОЛНЫЙ сквозной аудит логики сделки между водителем
(driver) и грузовладельцем (client) и выдать отчёт. НЕ додумывай — читай код и
подтверждай каждый факт ссылкой `файл:строка`. Где нашёл расхождение —
классифицируй как БАГ с severity (P0 блокер / P1 важный / P2 косметика).

## Правила работы
1. Сначала построй карту потока по коду, не по догадкам. Основные файлы:
   - Бэкенд: `backend/api/marketplace.py` (bids/deals/cargos/trips/статусы),
     `backend/api/notifications.py` (create_notification), `backend/api/chat.py`,
     `backend/services/push*.py` / `send_to_user`, `backend/database/deal_room_dal.py`.
   - Фронт: `App.js` (navigateFromUrl / routeFromUrl — маршрутизация пушей),
     `sw-template.js` (Service Worker notificationclick), `src/utils/pushNotifications.js`,
     `src/screens/CargoDetail.js`, `src/screens/TripDetail.js`, `src/screens/ChatScreen.js`
     (Deal Room), `src/screens/ChatsListScreen.js` (вкладка «Сделки»/Предложения),
     `src/screens/MyTripsScreen.js` (вкладки Мои/В работе/Завершённые),
     `src/components/deal/DealRoom.js`, `src/components/BidModal.js`,
     `src/utils/marketAPI.js`, `src/utils/i18n.js`.
2. Для КАЖДОГО действия зафиксируй матрицу: **кто нажал → какой endpoint →
   что записалось в БД → что ушло второй стороне (push / InApp / системное
   сообщение в чат / deal_event) → КУДА ведёт deeplink пуша → где это видно в
   UI у ОБЕИХ ролей**.
3. Проверяй ЗЕРКАЛЬНОСТЬ: сценарий «водитель ставит на груз клиента» и
   «клиент ставит на рейс водителя» должны быть симметричны. Ищи места, где
   роль/текст/получатель перепутаны.
4. Особое внимание — DEEPLINK-ам пушей. Карта соответствия (проверь в
   `App.js:navigateFromUrl`): `/cargos/{id}`→CargoDetail, `/trips/{id}`→TripDetail,
   `/deals/{id}`→ChatScreen(Deal Room, т.е. ЧАТ), `/chats/{room}`→ChatScreen,
   `/`→никуда (падает в дефолтный экран «Мои грузы»). Любой `url="/"` в бэке —
   это мёртвый deeplink = БАГ.

## Что именно проверить (чек-лист по фазам)

### Фаза 1. Размещение груза (client) и рейса (driver)
- CreateCargoScreen → POST /market/cargos: валидация полей, дата не в прошлом,
  фото в storage. Где появляется груз: у клиента «Мои грузы» (active), у
  водителей в ленте FeedScreen. Push подписчикам маршрута?
- CreateTripScreen → POST /market/trips: verification-gate (неверифицированный
  водитель НЕ должен опубликовать). Где виден рейс: «Мои рейсы» у водителя,
  лента «Машины» у клиента.

### Фаза 2. Ставка (BidModal → POST /market/bids)
- Оба направления (bid на cargo и bid на trip).
- Что получает владелец: push «💰 Ставка $X» → deeplink `/chats/{room}` (в чат),
  InApp «bid_created», создаётся chat_room, ставка видна в «Сделки →
  Предложения», плашка «N предложений» на карточке.
- Повторная ставка → 409 → режим Edit. bids_count +1.
- ВАЖНО проверить: правильный ли получатель и правильный ли текст роли
  (не «Водитель снизил цену», когда биддер — грузовладелец).

### Фаза 3. Торг: counter / decline_counter / reject / cancel
- counter_bid: владелец шлёт контр → push биддеру «🔁 Контр $X» → deeplink в чат.
- accept_counter: биддер соглашается → создаётся сделка, push ОБЕИМ сторонам.
- decline_counter: биддер отказался → ставка → pending, push владельцу (deeplink
  НЕ должен быть `/`).
- reject_bid: владелец отклонил → push биддеру, bids_count −1.
- cancel_bid: биддер отозвал → ДОЛЖЕН уходить push владельцу (проверь, что не
  молча), bids_count −1.

### Фаза 4. Принятие ставки (accept_bid → _finalize_accept_inline)
- В БД: cargo→taken/taken_by ИЛИ trip→booked/booked_by; выигравшая ставка
  accepted; ВСЕ конкурентные ставки → rejected (auto-reject) — и их авторы
  ДОЛЖНЫ получить уведомление «Ставка не выбрана» (проверь, что не молча);
  создаётся deals(status=accepted); пишется deal_event «bid_accepted».
- Push биддеру «✅ Ставка принята» → deeplink `/deals/{id}` (в Deal Room).
- Где появляется сделка: driver «Рейсы → В работе», client «Грузы → Везут»,
  обе роли «Сделки → Предложения» с активной сделкой; прогресс-бар «Принят».
- Груз/рейс исчезает из ленты (status taken/booked).
- Гонка double-accept: два одновременных accept не должны создать 2 сделки
  (проверь conditional UPDATE + rowcount → 409).

### Фаза 5. Статусы сделки (PATCH /market/deals/{id}/status)
Цепочка: accepted → in_progress → at_border → delivered; cancelled из любого
рабочего. Для КАЖДОГО перехода проверь ВСЕ 5 каналов:
- **Валидация перехода**: нельзя accepted → delivered (перескок). Идемпотентность
  (тот же статус → без шума). delivered/cancelled — терминальные.
- **Push** второй стороне (правильный текст с эмодзи, сумма в валюте листинга).
- **InApp** («deal_status» в колокольчике).
- **Системное сообщение в чат** — серая «пила» по центру с КОНКРЕТНЫМ текстом
  («🚛 Рейс начался», а НЕ безликое «Статус сделки изменён»).
- **deal_event** в immutable-timeline Deal Room.
- **Синхронизация trip.status**: in_progress/at_border→in_transit,
  delivered→delivered, cancelled→cancelled. deal.status и trip.status НЕ должны
  расходиться (баг, который ловил владелец: «не совпадает»).
- **UI обеих ролей**: прогресс-бар (4 шага), кнопка следующего шага, переезд
  карточки между вкладками (В работе → Завершённые), появление RatingModal при
  delivered, возврат груза в ленту при cancelled.
- Кнопки для driver на TripDetail И CargoDetail: наличие шага at_border
  (не должно быть accepted→in_progress→delivered, минуя границу).

### Фаза 6. Открытый вопрос ЛОГИКИ (дай рекомендацию, не меняй молча)
Сейчас пуш о смене статуса сделки ведёт в `/deals/{id}` = ЧАТ сделки (Deal Room).
Владелец сомневается, что это правильно — возможно, тап должен вести в КАРТОЧКУ
заказа / экран отслеживания (МойРейс/Везут с прогресс-баром и трекингом), а не в
переписку. Проанализируй паттерны inDrive/Uber Freight, опиши плюсы/минусы обоих
вариантов и дай чёткую рекомендацию: куда должен вести каждый тип пуша (ставка →
чат; смена статуса → ? ; доставлено → отзыв?). Это дизайн-решение — выведи его
отдельным разделом отчёта.

### Фаза 7. Отзывы после доставки
- delivered → RatingModal у обеих сторон. POST /reviews. Двусторонность.
- Где виден рейтинг, как влияет на скоринг водителя.

### Фаза 8. Крайние случаи
- Гостевой режим (hasToken && !session): что видно, что заблокировано.
- Верификационный гейт водителя.
- Отложенный deeplink: пуш пришёл, пока юзер не в авторизованном стеке —
  `pendingUrlRef` должен доиграть после логина (App.js).
- Дедуп нативного тапа (getLastNotificationResponseAsync + listener).
- Что если chat_room_id у сделки NULL — системные сообщения не должны падать.

## Формат отчёта
Выдай Markdown-отчёт:
1. **Матрица уведомлений** — таблица: Событие | Инициатор | Endpoint | Push (текст
   + deeplink) | InApp | Чат-сообщение | deal_event | UI-эффект driver | UI-эффект
   client. Строка на КАЖДОЕ событие.
2. **Список багов** — severity (P0/P1/P2), файл:строка, «ожидалось / фактически»,
   предлагаемый фикс.
3. **Расхождения зеркальности** — где driver↔client несимметричны.
4. **Мёртвые/неверные deeplink-и** — где пуш ведёт не туда.
5. **Рекомендация по Фазе 6** (куда должны вести пуши).
6. **Итог**: готово ли к запуску (go / no-go) и топ-5 обязательных фиксов.

Начинай с построения карты потока по коду. Не выдумывай — только подтверждённые
фактами (файл:строка) выводы.
